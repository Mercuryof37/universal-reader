# 部署与分享指南

> 本文说明**如何让别人在另一台设备上使用这个阅读器**。
>
> 核心事实：这是一个**纯静态、无后端**的应用。部署后服务端只是一堆静态文件，
> 看不到任何人的文档 —— 文档始终只留在使用者自己的浏览器里。
> 这一节决定了下面所有步骤都比常规 Web 应用简单。

---

## 一、三种方式的选择

| 场景 | 做法 | 对方需要做什么 | 何时适用 |
|---|---|---|---|
| 临时试用 | `npx vite --host` | 同一 WiFi 下打开链接 | 今天就想给人看，几小时 |
| **长期使用** | **部署 Cloudflare Pages** | **只需打开网址** | **推荐，本文重点** |
| 自备环境 | 源码 + `npm run dev` | 装 Node、跑命令 | 对方是开发者 |

选择 Pages 的理由不只是方便：**唯一一个对方不需要任何技术背景的方案**，
而且它不破坏"文档不出浏览器"这个核心定位。

---

## 二、部署到 Cloudflare Pages

走**仪表盘的 Git 集成**：推一次代码就永久生效，之后每次 push 都自动部署。

### 2.1 为什么不用 wrangler 配置文件

Cloudflare 允许用 `wrangler.toml` 配置 Pages，但**本项目不能用**：

| 冲突点 | 说明 |
|---|---|
| `main` vs `pages_build_output_dir` | `main` 是 Workers 专用字段，Pages 需要 `pages_build_output_dir`，两者不能共存于同一个文件 |
| 现有 `wrangler.toml` 的用途 | 它配置的是**可选的 API 代理 Worker**（`worker/api-proxy.ts`），与前端部署无关 |
| 源唯一性 | 一旦某字段由 wrangler 文件接管，**仪表盘上对应字段会变为只读** |

参见 [Cloudflare Pages 配置文档](https://developers.cloudflare.com/pages/functions/wrangler-configuration/)。

**结论**：前端走仪表盘，`wrangler.toml` 保持纯 Worker 用途。

### 2.2 前置准备

1. 代码推送到 GitHub 仓库（`.gitignore` 已排除 `node_modules`、`dist`、`.env.local`）
2. 一个 Cloudflare 账号（免费版即可）

### 2.3 创建项目

Cloudflare 仪表盘 → **Workers & Pages** → **Create** → **Pages** → **Connect to Git** → 选择仓库。

### 2.4 构建配置（**照抄下表**）

| 配置项 | 值 | 为什么是这个值 |
|---|---|---|
| Framework preset | `None` 或 `Vite` | 两者都可以，我们显式指定命令 |
| **Build command** | **`npm run build`** | ⚠️ **不能用 `vite build`**，见下方说明 |
| **Build output directory** | **`dist`** | Vite 的默认产物目录 |
| Root directory | 留空（或填仓库内项目子目录） | 仓库根就是项目根 |

### ⚠️ 构建命令必须用 `npm run build`

这不是风格问题。`package.json` 挂了两个钩子：

| 钩子 | 脚本 | 作用 |
|---|---|---|
| `prebuild` | `scripts/copy-pdfjs-wasm.mjs` | 复制 pdf.js 的 WASM 解码器到 `public/` |
| `postbuild` | `scripts/verify-dist.mjs` | 校验产物（缺解码器 / 有 sourcemap / pdfjs 混入入口包都会失败） |

**直接写 `vite build` 会跳过这两个钩子。** 缺解码器的表现是：
**扫描版 PDF 全部渲染成空白页，而且不报任何错** ——
本项目为此排查了很多轮（见 `docs/03-踩坑与修复记录.md` 缺陷 11）。

`npm run build` 走的是同一条路径：本地、CI、Pages 完全一致。

### 2.5 Node 版本 —— **必须显式设置**

Pages 的 **v3 构建系统不再从 `package.json` 的 `engines` 字段读取 Node 版本**。

已通过 `.node-version` 文件固定为 **22**（仓库根目录，内容就是 `22`）。
这是官方支持的两种方式之一，另一种是在仪表盘设置环境变量：

| 方式 | 位置 | 本项目采用 |
|---|---|---|
| `.node-version` / `.nvmrc` 文件 | 仓库根目录 | ✅ **已添加 `.node-version`** |
| `NODE_VERSION` 环境变量 | 仪表盘 → Settings → Environment variables | 备选 |

参见 [Cloudflare Pages Build image 文档](https://developers.cloudflare.com/pages/configuration/build-image/)。

> 为什么必须是 22：Vite 8 要求 Node `^20.19 || >=22.12`。
> 本地开发用的是 25，CI 用 22，都满足；Pages 若用了过旧的默认版本会直接构建失败。

### 2.6 环境变量 —— **可以不填**

| 变量 | 作用 | 不填的后果 |
|---|---|---|
| `VITE_TRANSLATE_ENDPOINT` | 云端翻译代理地址 | 翻译退化为**浏览器内置翻译** |
| `VITE_TTS_ENDPOINT` | 云端语音合成代理地址 | 朗读退化为**浏览器原生 TTS** |
| `VITE_DEFAULT_TRANSLATE_ENGINE` | 界面初始引擎 | 默认 `deepl` |

**不填任何变量时应用完整可用。** 这是当初刻意的设计：保证零配置也能跑起来。

## 三、部署后的功能边界

| 功能 | 状态 | 说明 |
|---|---|---|
| md / txt / pdf / epub 导入阅读 | ✅ | 全部在浏览器内完成 |
| 双语对照、批注、导出 JSON/Markdown | ✅ | |
| 朗读（浏览器原生 TTS） | ✅ | 音色取决于使用者的操作系统 |
| 扫描版 PDF 的 OCR | ✅ | 慢，见下方说明 |
| 云端翻译（DeepL / OpenAI） | ❌ | 需另行部署 API 代理 Worker |
| 云端高质量 TTS | ❌ | 同上 |

### 启用云端能力（可选）

1. 部署 `worker/api-proxy.ts`，并写入密钥：

```bash
npx wrangler secret put DEEPL_API_KEY
npx wrangler secret put OPENAI_API_KEY
npx wrangler secret put AZURE_SPEECH_KEY
npx wrangler secret put AZURE_SPEECH_REGION
npx wrangler deploy
```

2. 在 `wrangler.toml` 的 `[vars]` 里把 `ALLOWED_ORIGIN` 设为你的 Pages 域名
   （形如 `https://<项目名>.pages.dev`）

3. 在 Pages 的环境变量里填入 `VITE_TRANSLATE_ENDPOINT` 与 `VITE_TTS_ENDPOINT`

**`ALLOWED_ORIGIN` 的两个坑**：

- 不配置 → 代理会拒绝跨域请求，云端功能静默失效
- 配置错误或留空放行 → **代理会变成任何人都能白嫖你 API 额度的公开接口**

## 四、必须提前告知使用者的事

### 4.1 文档不会跨设备同步 —— 这是设计，不是缺陷

每台设备的书库都在**它自己浏览器的 IndexedDB** 里。因此：

- A 电脑导入的书，B 手机上打开看不到
- 各设备的批注相互独立
- 清除浏览器站点数据会**连带清空**已导入的文档与批注

这是"零后端、文档不上传"的必然结果。若做成同步，就必须有服务器存文档，
核心卖点随之消失。

**目前能跨设备搬运的只有批注**：批注侧栏支持导出 JSON / Markdown。
书本身需要重新导入一次。

> "全量数据导出 / 导入"尚未实现，列在路线图里。
> 若确实有跨设备需求，它比云同步简单得多，也不破坏隐私定位，值得优先做。

### 4.2 手机上的 OCR 会很慢

浏览器端 OCR 靠 CPU 单核跑。那本 833 页的扫描书在电脑上都要很久，
手机上更慢，且切到后台会被浏览器降频。

**建议**：手机只用来**读**；OCR 这类重活放在电脑上做，导入后的文档无法直接传到手机
（见 4.1），所以更实际的做法是——**需要 OCR 的书在电脑上处理完，
把原件发给对方，让对方自己导入**。

### 4.3 浏览器版本要求

| 浏览器 | 最低版本 | 原因 |
|---|---|---|
| Chrome / Edge | **119** | pdf.js 5 需要 `Promise.withResolvers`（ES2024）与 `Uint8Array#toHex`（ES2025） |
| Firefox | **121** | 同上 |
| Safari | **17.4** | 同上 |

应用内置了这些 API 的补齐实现并在能力不足时点名提示，但仍建议使用新版本浏览器。

### 4.4 没有 PWA，断网后打不开

目前没有 Service Worker，因此：

- 不能"添加到主屏幕"变成独立应用
- **断网后连页面本身都加载不出来**，已导入的书也读不了

"离线可读"是项目的核心约束之一，但目前只在"页面已加载"的前提下成立。
PWA 列在路线图 `R4`。

## 五、部署前的检查清单

```powershell
# 1. 完整构建（含钩子），并让产物校验把关
npm run build
#    期望：【verify-dist】构建产物校验通过

# 2. 本地预览生产产物（不是 dev！）
npm run preview
#    打开提示的地址，实际导入一份 PDF 与一份中文 txt 验证

# 3. 确认产物中不含 sourcemap
Get-ChildItem dist -Recurse -Filter *.map
#    期望：无输出

# 4. 确认 WASM 解码器已交付
Test-Path dist\pdfjs-wasm\jbig2.wasm
Test-Path dist\pdfjs-wasm\openjpeg.wasm
#    期望：都是 True
```

四条全部通过再推送。`npm run build` 里的 `postbuild` 钩子会自动检查 3 与 4，
所以第 1 步通过就意味着这两项没问题。

### 部署后必做的一次真实回归

打开 `https://<项目名>.pages.dev`，**实际导入三份文件**并各读一页：

1. 一份中文 `.txt` —— 验证编码识别（文档库标签应显示「编码：UTF-8」或「GB18030 / GBK」）
2. 一份**文字版** PDF —— 验证 pdf.js 与 Worker 正常
3. 一份**扫描版** PDF —— 验证 WASM 解码器已交付（应提示"是扫描版"并可选择 OCR，
   **而不是弹空白页或任何 toHex / workerSrc 报错**）

第 3 项是这次部署最需要验证的：**解码器缺失时唯一的症状就是"页面全白"**，
不看这一项无法确认部署成功。

## 六、常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 构建报 Node 版本错误 | Pages 默认 Node 过旧 | 确认 `.node-version` 已提交，或在仪表盘设 `NODE_VERSION=22` |
| 扫描版 PDF 全是空白页 | 构建命令用了 `vite build`，跳过了 `prebuild` 钩子 | 改回 `npm run build` |
| 云端翻译/TTS 静默失效 | 未配环境变量，或 Worker 的 `ALLOWED_ORIGIN` 不匹配 | 属预期降级；要启用见第 3 节 |
| 产物比预期大很多 | `build.sourcemap` 被改回 `true` | 关掉；`postbuild` 校验也会拦下 |
| PDF 报 `a.toHex is not a function` | 浏览器版本低于要求 | 升级浏览器；应用内置了补齐，能力不足时会点名提示 |
| OCR 提示"是扫描版"后长时间无进度 | 语言包约 22MB，首次需下载 | 等待；建议先用"前 10 页"试跑 |

## 七、成本

| 项 | 免费额度 | 本项目用量 |
|---|---|---|
| Cloudflare Pages 静态托管 | 无限带宽、每月 500 次构建 | 每次 push 触发一次，远低于上限 |
| Workers（API 代理，可选） | 每天 10 万次请求 | 取决于使用人数与翻译频率 |
| 翻译 API（可选） | DeepL 免费版每月 50 万字符 | 视口懒翻译 + 两级缓存已大幅降低消耗 |

**只部署前端的话，成本为零。** 云端能力才涉及第三方 API 计费，
而本项目默认不启用它们。
