# 部署与分享指南

> 本文说明**如何让别人在另一台设备上使用这个阅读器**。
>
> 核心事实：这是一个**纯静态、无后端**的应用。部署后服务端只是一堆静态文件，
> 看不到任何人的文档 —— 文档始终只留在使用者自己的浏览器里。
> 这一节决定了下面所有步骤都比常规 Web 应用简单。
>
> ⚠️ **一处例外（部署前必须知道）**：启用 Worker 之后，**SimpleTex 公式 OCR**
> 会把页面局部像素自动转发给第三方云服务。这与「文档全程不离开浏览器」的口径冲突，
> 详见 §4.5。默认（不部署 Worker）不涉及该功能。

> **本文已同步到提交 `aa8827a`**（2026-10-06）。当前生产地址：
> `https://universal-reader.pages.dev/`（Pages 项目名 `universal-reader`）；
> API 代理：Worker `universal-reader-api`，`https://universal-reader-api.616444703.workers.dev`。

## 一、三种方式的选择

| 场景 | 做法 | 对方需要做什么 | 何时适用 |
|---|---|---|---|
| 临时试用 | `npx vite --host` | 同一 WiFi 下打开链接 | 今天就想给人看，几小时 |
| **长期使用** | **部署 Cloudflare Pages** | **只需打开网址** | **推荐，本文重点** |
| 自备环境 | 源码 + `npm run dev` | 装 Node、跑命令 | 对方是开发者 |

选择 Pages 的理由不只是方便：**唯一一个对方不需要任何技术背景的方案**，
而且它不破坏"文档不出浏览器"这个核心定位 —— 唯一的例外是 §4.5 的公式 OCR
（它需要在可选 Worker 上额外配置密钥，不配置就不会外发任何数据）。

## 二、部署到 Cloudflare Pages

走**仪表盘的 Git 集成**：推一次代码就永久生效，之后每次 push 都自动部署。

### 2.1 为什么不用 wrangler 配置文件

Cloudflare 允许用 `wrangler.toml` 配置 Pages，但**本项目不能用**：

| 冲突点 | 说明 |
|---|---|
| `main` vs `pages_build_output_dir` | `main` 是 Workers 专用字段，Pages 需要 `pages_build_output_dir`，两者不能共存于同一个文件 |
| 现有 `wrangler.toml` 的用途 | 它配置的是**可选的 API 代理 Worker**（`worker/api-proxy.ts`），与前端部署无关 |
| 源唯一性 | 一旦某字段由 wrangler 文件接管，**仪表盘上对应字段会变为只读** |

参见 [Cloudflare Pages 配置文档](https://developers.cloudflare.com/pages/functions/wrangler-configuration/)。

**结论**：前端走仪表盘，`wrangler.toml` 保持纯 Worker 用途。

### 2.2 前置准备

1. 代码推送到 GitHub 仓库（`.gitignore` 已排除 `node_modules`、`dist`、`.env.local`）
2. 一个 Cloudflare 账号（免费版即可）

### 2.3 创建项目

Cloudflare 仪表盘 → **Workers & Pages** → **Create** → **Pages** → **Connect to Git** → 选择仓库。

### 2.4 构建配置（**照抄下表**）

| 配置项 | 值 | 为什么是这个值 |
|---|---|---|
| Framework preset | `None` 或 `Vite` | 两者都可以，我们显式指定命令 |
| **Build command** | **`npm run build`** | ⚠️ **不能用 `vite build`**，见下方说明 |
| **Build output directory** | **`dist`** | Vite 的默认产物目录 |
| Root directory | 留空（或填仓库内项目子目录） | 仓库根就是项目根 |

### ⚠️ 构建命令必须用 `npm run build`

这不是风格问题。`package.json` 挂了这些钩子：

| 钩子 | 脚本 | 作用 |
|---|---|---|
| `predev` / `prebuild` | `scripts/copy-pdfjs-wasm.mjs` + `scripts/make-icons.mjs` | 复制 pdf.js 的 WASM 解码器到 `public/`；生成 PWA 图标 |
| `postbuild` | `scripts/clean-onnx-wasm.mjs` **&&** `scripts/verify-dist.mjs` | **先删掉被打进 `dist/` 的 ONNX WASM**，再校验产物（缺解码器 / 有 sourcemap / pdfjs 混入入口包都会失败） |

`build` 脚本本身是 `tsc -b && vite build`，所以 `postbuild` 现在是**两个脚本串联**：
`clean-onnx-wasm.mjs && verify-dist.mjs`（`aa8827a` 时点的状态）。

**直接写 `vite build` 会跳过全部钩子**（连 `tsc -b` 也一起跳过）。缺解码器的表现是：
**扫描版 PDF 全部渲染成空白页，而且不报任何错** ——
本项目为此排查了很多轮（见 `docs/03-踩坑与修复记录.md` 缺陷 11）。

`npm run build` 走的是同一条路径：本地、CI、Pages 完全一致。

### ⚠️ ONNX WASM 必须走 CDN —— 单文件 25MB 上限

OCR 引擎（PaddleOCR）依赖 ONNX Runtime Web 的 `.wasm`，它约 **28MB**，
**超过 Cloudflare Pages 单文件 25MB 上限**：打进 `dist/` 就会部署失败。

因此从提交 `3d4a2ad` 起改为**运行时从 CDN 加载**：
`src/lib/ocrEngine.ts` 里设置
`ort.env.wasm.wasmPaths = https://cdn.jsdelivr.net/npm/onnxruntime-web@<版本>/dist/`，
并由 `postbuild` 的第一个脚本把产物里的那份删掉。实测构建日志：

```
Removed ort-wasm-simd-threaded.jsep-MDYUKy93.wasm (served from CDN at runtime)
Cleaned 1 ONNX WASM file(s) from dist.
```

`vite.config.ts` 里也加了 `globIgnores: ['**/ort-wasm*']`，避免它被预缓存清单收进去。

**代价（要写进对使用者的说明）**：首次执行 OCR 需要联网 ——
模型约 **10MB** 来自 **HuggingFace CDN**，ONNX WASM 约 **28MB** 来自 **jsDelivr**。
两者都只在**运行时缓存**里（`ocr-models`、`onnx-wasm`，均 CacheFirst），
**不在预缓存清单里**，也就是「用过一次之后才能离线用」。

### ⚠️ 本地构建的哈希 ≠ 线上构建的哈希

Cloudflare 的构建与本地构建**不是逐字节可复现的**。同一份源码：

| | 入口 chunk | PDF 解析 chunk |
|---|---|---|
| 本地 `dist/` | `index-BWQq926L.js` | `pdfParser-qWOY3aHL.js` |
| 线上（Pages） | `index-DewjVU_A.js` | `pdfParser-BC0kRy96.js` |

**绝不能用本地 `dist/` 里的文件名去推断线上资源名**（排查 PWA 陈旧 chunk 故障时踩过这个坑）。
要确认线上到底在跑什么，直接抓线上产物：

```powershell
$sw = (Invoke-WebRequest https://universal-reader.pages.dev/sw.js -UseBasicParsing).Content
$sw -match 'NetworkFirst'               # 期望 True：导航请求是网络优先
$sw -match 'html-navigation'            # 期望 True：导航缓存名
$sw -match 'createHandlerBoundToURL'    # 期望 False：修复后不应再出现
```

### 2.5 Node 版本 —— **必须显式设置**

Pages 的 **v3 构建系统不再从 `package.json` 的 `engines` 字段读取 Node 版本**。

已通过 `.node-version` 文件固定为 **22**（仓库根目录，内容就是 `22`）。
这是官方支持的两种方式之一，另一种是在仪表盘设置环境变量：

| 方式 | 位置 | 本项目采用 |
|---|---|---|
| `.node-version` / `.nvmrc` 文件 | 仓库根目录 | ✅ **已添加 `.node-version`** |
| `NODE_VERSION` 环境变量 | 仪表盘 → Settings → Environment variables | 备选 |

参见 [Cloudflare Pages Build image 文档](https://developers.cloudflare.com/pages/configuration/build-image/)。

> 为什么必须是 22：Vite 8 要求 Node `^20.19 || >=22.12`。
> 本地开发用的是 25，CI 用 22，都满足；Pages 若用了过旧的默认版本会直接构建失败。

### 2.6 环境变量 —— **可以不填**

这是**前端（Pages）侧**的变量：

| 变量 | 作用 | 不填的后果 |
|---|---|---|
| `VITE_TRANSLATE_ENDPOINT` | 云端翻译代理地址 | 翻译退化为**浏览器内置翻译** |
| `VITE_TTS_ENDPOINT` | 云端语音合成代理地址 | 朗读退化为**浏览器原生 TTS** |
| `VITE_DEFAULT_TRANSLATE_ENGINE` | 界面初始引擎 | 默认 `deepl` |

**不填任何变量时应用完整可用。** 这是当初刻意的设计：保证零配置也能跑起来。

> **Worker（服务端）侧的密钥是另一回事**，它们**绝对不能**写进 Pages 的前端变量，
> 而是用 `npx wrangler secret put` 写成加密环境变量：`DEEPL_API_KEY`、`OPENAI_API_KEY`、
> `AZURE_SPEECH_KEY`、`AZURE_SPEECH_REGION`，以及公式 OCR 用的 **`SIMPLETEX_API_KEY`**
> —— 最后一个不配置时 `/api/formula-ocr` **恒返回 500**（见 §三）。

## 三、部署后的功能边界

| 功能 | 状态 | 说明 |
|---|---|---|
| md / txt / pdf / epub 导入阅读 | ✅ | 全部在浏览器内完成 |
| 双语对照、批注、导出 JSON/Markdown | ✅ | |
| 数学公式渲染（KaTeX） | ✅ | 支持 `$行内$` 与 `$$块级$$`，纯前端、不需要网络 |
| 朗读（浏览器原生 TTS） | ✅ | 音色取决于使用者的操作系统 |
| PWA 离线打开（Service Worker） | ✅ 产物已核对 | 预缓存页面骨架 + 导航请求 NetworkFirst；**真实浏览器断网流程尚未验证**（见 §4.4） |
| 扫描版 PDF 的 OCR（PaddleOCR） | ⚠️ 未真机验证 | **首次必须联网**（模型约 10MB + ONNX WASM 约 28MB）；真实扫描件的中文识别准确率尚未验证 |
| 公式 OCR（SimpleTex，需 Worker） | ⚠️ 会外发数据 | 需 Worker + `SIMPLETEX_API_KEY`；**会把页面局部像素上传第三方**，见 §4.5 |
| 云端翻译（DeepL / OpenAI） | ❌ | 需另行部署 API 代理 Worker |
| 云端高质量 TTS | ❌ | 同上 |

### 启用云端能力（可选）

1. 部署 `worker/api-proxy.ts`，并写入密钥：

```bash
npx wrangler secret put DEEPL_API_KEY
npx wrangler secret put OPENAI_API_KEY
npx wrangler secret put AZURE_SPEECH_KEY
npx wrangler secret put AZURE_SPEECH_REGION
npx wrangler secret put SIMPLETEX_API_KEY     # 公式 OCR（/api/formula-ocr）必需，否则恒 500
npx wrangler deploy
```

2. 在 `wrangler.toml` 的 `[vars]` 里配置 `ALLOWED_ORIGIN`。**当前仓库里的值是**：

```toml
ALLOWED_ORIGIN = "https://universal-reader.pages.dev,https://*.universal-reader.pages.dev,http://localhost:5173"
```

`*` **只匹配单个 DNS 标签、不跨点**：`https://*.universal-reader.pages.dev` 能覆盖
Pages 每次推送生成的预览地址（`https://<hash>.universal-reader.pages.dev`），
但**覆盖不到生产地址** `https://universal-reader.pages.dev`，**生产地址必须单独列出**。
第三条 `http://localhost:5173` 供本地开发使用，不需要时删掉。

3. 在 Pages 的环境变量里填入 `VITE_TRANSLATE_ENDPOINT` 与 `VITE_TTS_ENDPOINT`
   （都指向这个 Worker 的地址 `https://universal-reader-api.616444703.workers.dev`）

**`ALLOWED_ORIGIN` 的三个坑**：

- 不配置 → 代理会拒绝跨域请求，云端功能静默失效（CORS 是 fail-closed 的）
- 配置错误或留空放行 → **代理会变成任何人都能白嫖你 API 额度的公开接口**
- 只写通配符（`*`、`https://*`）→ 这类规则会被**忽略**（否则白名单形同虚设）；
  只写 `https://*.universal-reader.pages.dev` 而漏掉生产地址 → 生产站点用不了云端功能

**改完必须 `npx wrangler deploy` 才生效**，否则跑的还是旧代码。

### `SIMPLETEX_API_KEY` 与 `/api/formula-ocr` 的行为

| 情况 | 行为 |
|---|---|
| 未配置 `SIMPLETEX_API_KEY` | `/api/formula-ocr` **恒返回 500 `未配置 SIMPLETEX_API_KEY`**；PaddleOCR 主流程仍然工作，公式部分退化为 PaddleOCR 的原始识别结果（客户端只告警） |
| 已配置 | Worker 以 `Authorization: Bearer <key>` 转发到 `https://server.simpletex.cn/api/v1/simpletex_recognize`（multipart 字段名 `file`），取回 `res.latex` |
| 图片过大 | 客户端上限 `MAX_IMAGE_SIZE = 2_000_000` 字节；服务端上限 **2,700,000** 个 base64 字符（约 2MB），超出返回 **413** |

## 四、必须提前告知使用者的事

### 4.1 文档不会跨设备同步 —— 这是设计，不是缺陷

每台设备的书库都在**它自己浏览器的 IndexedDB** 里。因此：

- A 电脑导入的书，B 手机上打开看不到
- 各设备的批注相互独立
- 清除浏览器站点数据会**连带清空**已导入的文档与批注

这是"零后端、文档不上传"的必然结果。若做成同步，就必须有服务器存文档，
核心卖点随之消失。

**目前能跨设备搬运的只有批注**：批注侧栏支持导出 JSON / Markdown。
书本身需要重新导入一次。

> "全量数据导出 / 导入"尚未实现，列在路线图里。
> 若确实有跨设备需求，它比云同步简单得多，也不破坏隐私定位，值得优先做。

### 4.2 手机上的 OCR 会很慢，而且首次必须联网

浏览器端 OCR 靠 CPU 单核跑（引擎是 PaddleOCR，跑在 ONNX Runtime Web 的 WASM 上）。
那本 833 页的扫描书在电脑上都要很久，手机上更慢，且切到后台会被浏览器降频。

而且**第一次执行 OCR 一定要联网**：模型约 **10MB**（HuggingFace CDN）+ ONNX WASM 约 **28MB**
（jsDelivr）都要在运行时下载，**用过一次之后才进入缓存、才能离线用**。
国内网络对这两个 CDN 的可达性都不保证 —— 下不动时会报「首次使用需下载模型（约 10MB），请检查网络后重试」
（初始化超时阈值是 180 秒）。

**建议**：手机只用来**读**；OCR 这类重活放在电脑上做，导入后的文档无法直接传到手机
（见 4.1），所以更实际的做法是——**需要 OCR 的书在电脑上处理完，
把原件发给对方，让对方自己导入**。

### 4.3 浏览器版本要求

| 浏览器 | 最低版本 | 原因 |
|---|---|---|
| Chrome / Edge | **119** | pdf.js 5 需要 `Promise.withResolvers`（ES2024）与 `Uint8Array#toHex`（ES2025） |
| Firefox | **121** | 同上 |
| Safari | **17.4** | 同上 |

应用内置了这些 API 的补齐实现并在能力不足时点名提示，但仍建议使用新版本浏览器。

### 4.4 PWA 已上线：断网能打开，但仍有前提

Service Worker 已经落地（`vite-plugin-pwa`，`sw.js` 随产物生成）：

- 预缓存页面骨架（实测 `precache 18 entries (3578.19 KiB)`），断网也能打开页面
- 导航请求走 **NetworkFirst**（`html-navigation`）：**在线拿最新 HTML**，避免"旧 HTML 引用已被删除的 chunk"
- 离线冷启动由 `seedNavigationFallback()` 兜底：注册成功时趁在线把 `/` 写进导航缓存，
  解决"装好之后第一次断网打开是白屏"的空档

**必须同时告诉使用者的前提**：

- **首次装载需要联网**：没联网加载过一次，就没有任何可离线的内容
- **首次 OCR 需要联网**（见 4.2）：模型与 ONNX WASM 只在运行时缓存里，不在预缓存清单里
- **真实浏览器里的断网流程目前尚未验证**（"加载 → 刷新一次 → DevTools 切 Offline → 刷新"这一步没做过）。
  产物层面已核对（线上 `sw.js` 含 `NetworkFirst`、不含 `createHandlerBoundToURL`），但这不等于离线行为已被验证

> 另有一处**未解决的设计冲突**（`registerType: 'autoUpdate'` 会自动重载页面，而代码是按
> prompt 模式写的、提示条永不出现），属于产品决策项，见仓库 `HANDOFF.md` §5.7。

### 4.5 ⚠️ 公式识别会把局部截图发到第三方云服务

这是**唯一一条"文档内容离开本机"的路径**，部署启用 Worker 后必须主动告知使用者：

- 触发方式：**自动**。OCR 识别出「像公式」的词簇（≥2 个相邻、置信度 < 70 等启发式）后，
  就会把该区域四周留 10% padding 裁剪成 PNG，POST 到自建 Worker 的 `/api/formula-ocr`，
  再由 Worker 转发给第三方 SimpleTex（`https://server.simpletex.cn/api/v1/simpletex_recognize`）
- **不需要用户逐次确认**，界面上也没有开关
- 失败时只告警，**保留 PaddleOCR 的原始识别结果**，不影响其余正文识别
- 不部署 Worker、或不配置 `SIMPLETEX_API_KEY` 时，这条路径不可用（恒 500），
  文档内容不会外发 —— 这也是一种可选的"零上传"配置

> 该功能是否保留、是否改为"仅对用户手动框选的区域调用"，目前**待决策**（见仓库 `HANDOFF.md` §5.7）。

## 五、部署前的检查清单

```powershell
# 1. 完整构建（含钩子），并让产物校验把关
npm run build
#    期望：PWA v1.3.0  mode generateSW  precache 18 entries (3578.19 KiB)
#          Removed ort-wasm-simd-threaded.jsep-MDYUKy93.wasm (served from CDN at runtime)
#          Cleaned 1 ONNX WASM file(s) from dist.
#          [verify-dist] 构建产物校验通过

# 2. 本地预览生产产物（不是 dev！）
npm run preview
#    打开提示的地址，实际导入一份 PDF 与一份中文 txt 验证

# 3. 确认产物中不含 sourcemap
Get-ChildItem dist -Recurse -Filter *.map
#    期望：无输出

# 4. 确认 WASM 解码器已交付
Test-Path dist\pdfjs-wasm\jbig2.wasm
Test-Path dist\pdfjs-wasm\openjpeg.wasm
#    期望：都是 True

# 5. 确认 ONNX WASM 已被清理（它必须走 CDN，28MB 超单文件上限）
Get-ChildItem dist -Recurse -Filter 'ort-wasm*'
#    期望：无输出
```

五条全部通过再推送。`npm run build` 里的 `postbuild`
（`clean-onnx-wasm.mjs && verify-dist.mjs`）会自动处理并检查 3、4、5，
所以第 1 步通过就意味着这三项没问题。

### 部署后必做的一次真实回归

打开 `https://universal-reader.pages.dev/`（或自己的 Pages 地址），**实际导入三份文件**并各读一页：

1. 一份中文 `.txt` —— 验证编码识别（文档库标签应显示「编码：UTF-8」或「GB18030 / GBK」）
2. 一份**文字版** PDF —— 验证 pdf.js 与 Worker 正常
3. 一份**扫描版** PDF —— 验证 WASM 解码器已交付（应提示"是扫描版"并可选择 OCR，
   **而不是弹空白页或任何 toHex / workerSrc 报错**）。
   这一步同时是**首次 OCR 的唯一验证机会**：注意它需要联网下载模型（约 10MB）与
   ONNX WASM（约 28MB），并观察中文识别结果是否可读

第 3 项是这次部署最需要验证的：**解码器缺失时唯一的症状就是"页面全白"**，
不看这一项无法确认部署成功。

> 注意：Cloudflare 构建出的资源名与本地不同（见 §2.4 的哈希对照表），
> 所以**部署后要核对线上资源，就抓线上产物**，不要拿本地 `dist/` 去比。

### 推送代码时：`github.com:443` 时通时断

本机实测 `github.com:443` **时通时断**（DNS 正常，`api.github.com:443` 与
`universal-reader.pages.dev:443` 可达，但 `github.com:443` 多数尝试失败；
本机未配 SSH key，也没有代理）。`git push` **重试 1–3 次内能成功**：

```powershell
# 失败就重试；不要因为一次 TLS/连接错误就去改 remote 或怀疑凭据
git push origin main
```

看到 `Recv failure` / `Connection was reset` 之类错误时，**先原样重试**。

## 六、常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 构建报 Node 版本错误 | Pages 默认 Node 过旧 | 确认 `.node-version` 已提交，或在仪表盘设 `NODE_VERSION=22` |
| 扫描版 PDF 全是空白页 | 构建命令用了 `vite build`，跳过了 `prebuild` 钩子 | 改回 `npm run build` |
| 部署失败 / 提示文件超过 25MB | ONNX WASM（约 28MB）没被清出 `dist/` | 用 `npm run build`；`postbuild` 的 `clean-onnx-wasm.mjs` 会删掉它并改走 CDN |
| 云端翻译/TTS 静默失效 | 未配环境变量，或 Worker 的 `ALLOWED_ORIGIN` 不匹配 | 属预期降级；要启用见第 3 节 |
| 产物比预期大很多 | `build.sourcemap` 被改回 `true` | 关掉；`postbuild` 校验也会拦下 |
| PDF 报 `a.toHex is not a function` | 浏览器版本低于要求 | 升级浏览器；应用内置了补齐，能力不足时会点名提示 |
| OCR 长时间无进度，随后报"检查网络" | **首次必须联网**：模型约 10MB（HuggingFace CDN）+ ONNX WASM 约 28MB（jsDelivr），全在运行时下载；初始化超时 180 秒 | 先联网跑通一次（之后进缓存可离线）；国内网络对这两个 CDN 可达性不保证 |
| 公式 OCR 恒返回 500 `未配置 SIMPLETEX_API_KEY` | Worker 缺少加密环境变量 | `npx wrangler secret put SIMPLETEX_API_KEY` 后 `npx wrangler deploy`；不配也不影响 PaddleOCR 主流程 |
| 公式 OCR 返回 413 | 图片超过服务端上限 2,700,000 个 base64 字符（约 2MB） | 属预期；裁剪到公式区域后再试 |
| 线上资源名与本地 `dist/` 不一致 | Cloudflare 构建与本地构建**不是逐字节可复现的** | 正常现象；核对线上请直接抓线上产物（见 §2.4） |
| 断网后连页面都打不开 | 这台设备没联网加载过一次（没有预缓存），或清过站点数据 | 先联网打开一次；见 4.4 |
| 读到一半页面自动刷新 | `registerType: 'autoUpdate'` 的 SW 激活时会 `window.location.reload()`（**待决策项**，提示条不会出现） | 目前没有用户开关，见 4.4 与仓库 `HANDOFF.md` §5.7 |
| `git push` 报连接被重置 / Recv failure | 本机 `github.com:443` 时通时断 | **原样重试 1–3 次**；不要改 remote 或怀疑凭据 |

## 七、成本

| 项 | 免费额度 | 本项目用量 |
|---|---|---|
| Cloudflare Pages 静态托管 | 无限带宽、每月 500 次构建 | 每次 push 触发一次，远低于上限 |
| Workers（API 代理，可选） | 每天 10 万次请求 | 取决于使用人数与翻译频率 |
| 翻译 API（可选） | DeepL 免费版每月 50 万字符 | 视口懒翻译 + 两级缓存已大幅降低消耗 |
| 公式 OCR（SimpleTex，可选） | **第三方云服务，额度与计费条款以其官方说明为准**（本项目的代码里没有配额控制） | 仅在 OCR 检测到公式候选区域时自动调用；不配 `SIMPLETEX_API_KEY` 则完全不调用 |

**只部署前端的话，成本为零。** 云端能力才涉及第三方 API 计费，
而本项目默认不启用它们。
