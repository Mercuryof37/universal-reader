# 翻译功能优化路线图

> 基于仓库 `aa075b9`（2026-10-12）及当前源码整理。本文是建议路线，不代表已承诺排期。实施前应以最新 `git log` 和代码复核状态。

## 1. 目标与设计原则

把翻译从“开启双语后自动翻译可见段落”扩展成三种互补动作：

1. **整段双语阅读**：沿用当前视口懒翻译，用户滚到哪里再翻到哪里。
2. **选中即译**：在选区浮动工具条里翻译选中的词、短语或句子，结果贴近原文出现。
3. **划词查词**：对单词展示词性、常见释义、发音和上下文例句；整句或长选区则切到短句翻译。

默认只处理用户选中的内容；不因为查一个词就翻译整段或全文。任何把正文送到云端的动作都应沿用项目现有的显式授权、代码层拦截、去向说明三项隐私约束。浏览器内置引擎、云端引擎、词典来源分别标明，避免把“浏览器内置”误当成所有浏览器都可用。

## 2. 当前技术基线

| 能力 | 当前实现 | 对路线图的影响 |
|---|---|---|
| 双语翻译 | `translationService.ts` 支持 DeepL、OpenAI 代理和浏览器 `Translator` API | 复用引擎和代理，不另造第二套整段翻译通道 |
| 按需翻译 | `useViewportTranslation.ts` 按视口排队，最多 3 个并发，可取消；面板可显式翻全文 | 当前已满足“不默认翻全文”；后续关注请求数、排队优先级和字符成本 |
| 译文缓存 | 内存译文 + IndexedDB，缓存跨文档共享 | 现有缓存 ID 使用 32 位哈希，选区高频缓存扩量前先加原文校验并升级键；目前缓存键也不区分引擎 |
| 选区与定位 | `BlockRow.tsx` 已取得选区文本、块 ID、块内字符偏移和浮动位置；`ReaderView.tsx` 有高亮、笔记等工具条 | 可在现有工具条加“翻译 / 查词”，不需要先重做文本选择 |
| 隐私授权 | 云端翻译默认关闭，设置里说明段落正文发往自建 Worker，再转发 DeepL / OpenAI | 选区翻译默认只发送选中文本；不能悄悄附带整段上下文 |
| 浏览器内置翻译 | 已做特性检测、语言检测与有效 BCP 47 源语言处理；无能力时安静降级 | Firefox 默认死路和非法 `sourceLanguage: 'auto'` 属于历史问题，当前实现已修正；仍是有限支持能力，不作为跨浏览器默认路径 |
| 技术路线文档 | `docs/技术路线图-四功能.md` 仍有早期翻译现状与优先项；HANDOFF 主要记录 OCR、隐私等近期工作 | 早期路线中已落地的默认引擎与隐私问题不要重复排期；每阶段开始前复核实现 |

### 需要继续保留的项目约束

- 文档导入、解析、保存和批注以本地为主；云端翻译必须明确告知并由用户主动开启。
- API 密钥只保存在 Worker，不进入前端。
- 翻译是按字符计费的云服务：缓存、按需、取消和成本提示是核心功能，不是后补优化。
- PDF、OCR 与 Markdown 的底层文本形态不同。首版只做已提取文本上的选择，不承诺图片文字、公式或版面错序时的查词准确性。

## 3. 推荐路线与验收门槛

### 阶段 0：把现有翻译的安全与正确性底座钉牢

**目标**：让新选区入口复用可信的引擎、缓存与授权机制。

- 将翻译缓存升级为更强的键，并在缓存行存储可核对的原文长度及短前缀；不匹配时按未命中处理，避免碰撞返回别段译文。
- 明确缓存与“换引擎后是否重译”的关系；在设置中提供清理译文缓存的动作，避免用户误以为切换引擎会刷新旧译文。
- 检查浏览器 Translator 实例的复用和生命周期；语言对变化时销毁旧实例，避免逐块创建。
- 为“翻译全文”呈现未翻译字符估算和确认提示；累计已发云端字符只在确实发生网络请求时计入，缓存命中不计。

**验收**：缓存错配不能静默命中；切引擎、清缓存行为清楚；云端同意关闭时零请求；全文翻译前能看到明确的字符估算。现有浏览器能力检测、有效源语言标签和安静降级继续作为回归约束，不应当重复排成待办。

### 阶段 1：选区即时翻译（首个用户可见里程碑）

**交互**：选中文字后，现有浮动工具条增加“翻译”。点击后在工具条下方或侧栏显示原文、译文、目标语言、引擎和加载状态；支持复制译文、再次翻译、关闭。用户无需打开全文双语模式。

**实现建议**：

- 复用 `BlockSelection`，向翻译服务增加针对任意字符串的入口；不要伪造完整 `ContentBlock`。
- 选区短于词级阈值时提示“查词”，词组和句子显示“翻译”。阈值先按长度/词数启发式实现，之后用实际阅读样例调整。
- 选区跨块时先支持 `window.getSelection()` 取得的完整文本并限制最大字符数；锚点只在单块选区上保存精确字符范围。超限时提示缩短选区，不自动扩大请求。
- 默认请求体只包含选中原文与目标语言。邻近上下文可能提升词义消歧，但属于额外正文外发；只有在界面提供单独、明确的“附带上下文以提高准确度”选项后才发送。
- 结果可临时保留在本次阅读状态并复用 IndexedDB 缓存；为缓存键完成阶段 0 的校验后再启用持久化。
- 阅读器内置引擎优先用于本地即时翻译；云端引擎要求既有 `cloudTranslationConsent`。选区是更小的数据范围，但不得把现有“段落正文”授权文案模糊扩张成全选区授权；更新说明应讲清确切发送的数据。

**验收**：选一词、一短语、一整句都能在原地得到结果；快速连续选择时旧请求不会覆盖新结果；关闭弹窗或切换文档后不会污染其他块；关闭云端授权时云端选区翻译不会请求；跨块选区可翻译但不生成错误锚点；PDF/OCR 选区保留原始提取文本并清楚显示来源限制。

### 阶段 2：划词查词与阅读型词典

在阶段 1 的弹层中增加词条模式，逐步加入：

- 词性和常见释义、英美音标或语音、例句与当前句上下文；支持复制、收藏和跳转到上下文。
- 区分单词查询和短语/句子翻译，提供快捷键和可配置的自动弹出行为；默认建议点击工具条触发，避免用户拖选时频繁遮挡。
- 词典数据优先采用公开授权、可离线打包的轻量词库；核实词库许可、中文覆盖、释义质量和资源大小后再选型。在线词典/API 作为可选提供方，逐个列明请求去向、授权与限额。
- 收藏词条存本地 IndexedDB，支持导出；不把批注、整段文档或阅读历史随词典请求上传。
- 允许用户查看多个来源的释义，但界面要能区分词典释义与机器翻译，不把机器翻译伪装成权威词义。

**验收**：单词和固定短语有稳定的词条结果；无词条时明确退化为短文本翻译；断网时已缓存/本地词典仍可查；收藏数据可导出且没有隐式云同步。

### 阶段 3：页面翻译效率和大段双语质量

- 保留视口懒翻译作为默认模式，滚动时优先翻译当前可见内容，降低远处预取优先级；停止、切文档和切语言时取消过期队列。
- 评估按多个段落合并为批请求以减少往返。须由 Worker 与前端共同实现，保留批失败拆分重试，缓存仍按每段分别写入。先测 DeepL / OpenAI 各自限制和真实延迟，禁止仅凭假定上调并发。
- 增加可见状态：当前段翻译中、已译数量、失败可重试、字符估算、缓存命中。错误只显示在用户主动操作或可处置的位置。
- 改进左右对照的阅读连续性：先做句子切分与保守对齐；句数不一致时退回段落布局，不做猜测式强制配对。
- 术语表放在后续：先选定引擎是否支持原生 glossary。只给确实命中当前段落的术语；若只能后处理替换，标注可能破坏语法，不对用户承诺完全一致。

**验收**：滚动快时不重复发请求；取消后旧结果不会写回；批量失败能恢复单段翻译；左右对齐无法确信时明确退化；长文成本与进度可见。

### 阶段 4：扩展生态与外部工具桥接（有需求再做）

- **不依赖 Google Translate 插件的私有接口**：官方扩展支持选中文本后从扩展图标或右键菜单翻译；Chrome 页面翻译是浏览器自己的能力。Chrome 允许网页向指定扩展发送消息，但目标扩展必须主动在 manifest 中允许本站 origin 并实现协议；没有可供网页通用发现、调用任意已安装扩展的接口。Google Translate 扩展未见公开的站点调用协议，不能把它当作 API。
- 首选开放互操作：选中文本后提供“复制原文”“在新标签打开翻译服务”等用户主动动作；外部服务是否接收文本、是否带上下文必须明确说明。仅拼接第三方 URL 前先验证其公开支持方式和隐私边界，不把非官方 URL 参数当 API 契约。
- 如果确有核心用户需要与 Saladict 或 Google 插件深度联动，独立评估发布浏览器 companion extension：以受限消息协议接收用户明确选择的文本，只开放当前文档和选区，不获取文档全文；维护 Chrome / Firefox 兼容和扩展商店发布成本。它应是可选项目，不让主 PWA 依赖扩展存在。
- 通过浏览器扩展访问 app 的 DOM/选区也受权限、页面类型和浏览器策略限制。PDF 插件视图、内嵌 frame 和移动浏览器需要单独验证，不能许诺所有场景都能由第三方插件划词。

**决策门**：只有阶段 1/2 的自带体验已验证仍有明显缺口，且用户愿意承担扩展安装、权限说明和双端维护时，才进入 companion extension 原型。

## 4. 优先级建议

| 优先级 | 内容 | 价值 | 主要成本/风险 |
|---|---|---|---|
| P0 | 缓存键与原文校验、引擎/授权边界、全文成本提示 | 避免错译和意外花费，为新入口兜底 | IndexedDB 迁移和旧缓存处理 |
| P1 | 在现有选区工具条加短文本翻译 | 最短路径解决“选定部分而不是翻全文” | 选区 DOM 与模型文本偏移差异；移动端选区交互 |
| P1 | 词/短语查词弹层与复制、发音 | 对应沙拉查词的核心阅读价值 | 词库许可、体积、数据质量 |
| P2 | 视口队列优先级、批量请求、句级保守对齐 | 降低延迟与请求数量，改善长文双语阅读 | Worker 协议变更和批失败处理 |
| P3 | Google/Saladict 深度扩展桥接、全离线 NMT | 生态互通或本地翻译覆盖 | 外部接口不可控、权限和维护成本；本地模型下载体积大 |

## 5. 本轮建议的实际切入点

已按用户确认的方向开始实施：先做 **缓存自校验 + 选区即时翻译**，形成闭环：选词 → “查词 / 翻译” → 原地看译法 → 复制。当前“查词”显示的是站内翻译译法，词性、权威词典释义和例句尚未接入，界面应如实说明。

大段文本的免费路径优先使用站内的浏览器 Translator API：用户在设置中选择“浏览器内置（本机）”，再触发视口或全文翻译；浏览器会话复用，对较长块使用流式翻译。它不调用 Google 翻译或沙拉查词扩展。网页直接调用指定的第三方扩展只有在该扩展主动配置 `externally_connectable`、允许本网站 origin 并实现消息协议时才可行；Chrome 扩展官方文档说明了这类前提，但 Google 翻译扩展没有公开站点消息 API 文档。因此当前不依赖其私有接口或扩展 ID，若以后需要深度联动，应由本项目提供可选 companion extension。

此方案沿用现有引擎和授权，不把选中查词扩大为段落或全文上传；浏览器不支持本机 Translator API 时，仍由用户显式选择并授权现有云端引擎。
