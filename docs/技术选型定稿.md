## 一、先把约束钉死

选型不是"选最好的技术"，而是"在约束下选最不容易后悔的技术"。本项目的约束有六条，它们是下面所有决策的依据：

| 编号 | 约束 | 对选型的直接影响 |
|---|---|---|
| C1 | **零后端**：文档不上传，没有服务器可写 | 不能有 SSR、不能有服务端 API 路由、不能依赖服务端会话 |
| C2 | **离线可用**：断网也要能读已导入的书 | 依赖必须能打包进浏览器；运行时不得强依赖网络 |
| C3 | **隐私是卖点**：用户上传的是私人文档 | 解析、存储、批注全在本地；密钥一律不进前端 |
| C4 | **要解析大文件**：PDF 动辄几十 MB | 解析必须离开主线程；内存策略比算法技巧更重要 |
| C5 | **有续费型外部 API**：翻译按字符计费 | 必须有缓存层与"按需调用"策略，否则账单不可控 |
| C6 | **单人开发、静态托管**（Cloudflare Pages） | 运维复杂度必须压到接近零，拒绝自建服务 |

**结论：这是一个"本地优先（local-first）应用"，不是网站。** 这个定位一旦确认，Next.js 一类的全栈框架就从候选名单里出局了——它们解决的问题（服务端渲染、服务端数据获取、API 层）在这个项目里一个都不存在，只会带来额外的构建复杂度。

### 1.1 约束的实测修正（2026-10-06 同步）

上面六条仍然是决策依据，但有两处**已被实测与后续功能打破或加上了前提**，必须写在这里，否则会被当成"已经满足了"：

| 约束 | 新增的前提 / 张力 | 状态 |
|---|---|---|
| **C2 离线可用** | ① **首次 OCR 需要联网**：PP-OCRv6 模型约 10MB（HuggingFace CDN）+ ONNX Runtime WASM 约 28MB（jsDelivr CDN），两者只进**运行时缓存**、不在预缓存清单里 —— 即「用过一次之后才能离线用」。② 公式增强需要联网，离线时该步骤失败但**不影响其余识别结果**。③ 模型与 WASM 两个 CDN **在国内的可达性都不保证**，而它们不是可选优化：缺任一个 OCR 完全不可用 | 口径需修正 |
| **C3 隐私是卖点** | **公式 OCR 曾经把文档像素自动送到第三方**：`enhanceFormulaRegions()` 原先检测到公式候选区域就上传，不需要用户逐次确认。**本轮已收口为默认关闭的显式开关（opt-in）**：`settingsStore.formulaOcrEnabled` 默认 `false`，用户必须在 OCR 对话框勾选「上传公式区域以换取更准的公式」；不勾选时引擎在 `detectFormulaRegions()` **之前**早退、上传函数 `recognizeFormula()` 自身也会抛错拒绝，**不发起任何网络请求 —— 默认路径零上传**。残余点：勾选后仍上传到第三方 `server.simpletex.cn`（经自建 Worker 转发）、需要联网、Worker 未配 `SIMPLETEX_API_KEY` 时该端点 500（线上实测当前就是 500）、没有上传审计视图 | **已决策**（默认关闭的显式 opt-in）；真机行为**未验证** |
| **C6 静态托管** | ONNX WASM 约 28MB，**超过 Cloudflare Pages 单文件 25MB 上限**，无法随站点发布，只能运行时从 jsDelivr 拉取 | 已用构建脚本绕过 |

## 三、定稿技术栈

### 3.1 核心（已落地并有构建产物验证）

| 层次 | 定稿 | 为什么是它 | 为什么不是别的 |
|---|---|---|---|
| 构建工具 | **Vite 8** | 开发服务器冷启动毫秒级；Rolldown 打包；原生支持 `?url` / `?worker`，PDF Worker 接起来只有一行 | Webpack 配置负担重；Parcel 生态弱 |
| 语言 | **TypeScript 5.9（strict）** | 内容模型是四种格式的公共契约，类型错了整个渲染层都会崩 | 纯 JS 在 `ContentBlock` 这种多层嵌套结构上无法自保 |
| UI 框架 | **React 19** | 虚拟滚动、批注选区、TTS 状态机都是"状态驱动视图"，React 的模型最贴合 | Svelte 体积更小但生态与 AI 辅助成熟度略逊；Vue 亦可，但初版方案的 UI 描述基于 React |
| 样式 | **Tailwind CSS 4** | v4 的 CSS-first 配置让主题令牌直接写成 CSS 变量，正好契合"宣纸/米黄/夜读"三主题 | CSS-in-JS 运行时开销大；纯 CSS 在虚拟列表里维护成本高 |
| 无样式组件 | **`@base-ui/react`** | 只提供开关、下拉、弹层的交互逻辑与无障碍支持，外观完全自控 | 直接用原生 `<select>` 也行，但弹层与焦点的无障碍要自己写 |
| 图标 | **lucide-react** | 按需 tree-shake，风格统一 | 图标字体无法按需、SVG 手写维护成本高 |

### 3.2 数据与状态

| 层次 | 定稿 | 为什么是它 |
|---|---|---|
| 持久化 | **IndexedDB + Dexie 4** | localStorage 只有约 5MB 且只能存字符串，一本带译文的书轻松超过；Dexie 把原生的回调+游标写法变成接近数组操作 |
| 内存状态 | **Zustand 5** | 只有一个 store 的订阅粒度问题，不需要 Redux 的样板；`persist` 中间件恰好满足"设置存 localStorage、正文存 IndexedDB"的分层 |
| 分层原则 | 设置 → localStorage；正文/批注/译文/进度 → IndexedDB | 混在一起会导致改一次字号就触发一次数据库写入 |

**表结构（`src/lib/db.ts`）**

```
documents    id, title, format, metadata.created, metadata.modified   ← 文档元信息（列表页只读这张表）
blocks       docId                                                    ← 正文与目录，一篇一行，整篇原子写入
annotations  id, docId, blockId, type, createdAt                      ← 批注
progress     docId, updatedAt                                         ← 阅读进度（与正文分离，避免翻页重写整篇）
translations id(=hash(原文)+目标语言), targetLang, createdAt           ← 译文缓存，跨文档复用
```

### 3.3 解析层

| 格式 | 定稿 | 关键实现要点 |
|---|---|---|
| Markdown | `unified` + `remark-parse` + `remark-gfm`，**新增 `remark-math`** | 解析成 mdast 后**拍平**为线性数组：阅读器的滚动、朗读、批注三件事都按"段"为单位，树结构在这三处都要额外遍历，收益为负。`remark-math` 让 `$行内$` / `$$块级$$` 进入解析 |
| 纯文本 | 自研（约 90 行） | 三级降级分段：空行分段 → 单行分段 → 整篇一块。不能出现"0 块文档" |
| PDF | `pdfjs-dist` 5（Worker 内解析） | PDF 没有"段落"概念，只有绝对定位的文字片段。按 y 聚类成行 → 按行距聚成段；扫描件无文字层时**明确报错**而不是返回空文档 |
| EPUB | `epubjs` | 直接拿到按阅读顺序排好的 spine；单章损坏时跳过该章而不是整本失败 |
| **扫描件 OCR** | **`ppu-paddle-ocr@^6.6.0` + `onnxruntime-web@^1.30.0`**（PP-OCRv6 small 模型，ONNX Runtime Web 在浏览器内推理） | 引擎从 `tesseract.js` **整体更换**，见 3.3.1 |
| **数学公式渲染** | **`katex@^0.19.0`** | 公式不能当普通文本渲染，否则上下标与符号全丢。见 3.3.2 |
| **公式 OCR** | **SimpleTex 云服务**，经 Worker 转发，**默认关闭的显式开关** | 应用中**唯一**一条把文档内容送出本机的路径；默认零上传，需用户在识别前勾选。见 3.3.3 |

**注册表模式**：新增格式 = 写一个实现 `FileParser` 的类 + 注册一行，其余代码不动。

#### 3.3.1 OCR 引擎更换：为什么是 PaddleOCR，代价是什么

`cdf2957`（13 个文件，+1245 / −322 行）把引擎整体换掉。**理由只有两条，但都指向中文扫描件的真实痛点**：

1. **PP-OCR 专为中文训练，中文准确率远超 Tesseract。**
2. **50+ 语言全字典，无需手动选语言包** —— 语言选择从用户面前消失，选错语言导致整页崩坏这一整类问题不复存在。

**运行方式**：ONNX Runtime Web（**WASM，全程在浏览器内**），模型为 `V6_SMALL_MODEL`（PP-OCRv6 small），经 `ppu-paddle-ocr/web` 的 `PaddleOcrService` 调用。`src/lib/ocrEngine.ts` 因此重写为 **549 行**（本轮又为公式上传开关加了两行判断与一段说明，原为 540 行）。

**必须记住的代价**：

| 代价 | 具体值 | 影响 |
|---|---|---|
| 首次使用需联网 | 模型约 **10MB**（HuggingFace CDN）+ ONNX WASM 约 **28MB**（jsDelivr） | 缓存在 `ocr-models` / `onnx-wasm`（CacheFirst），**不在预缓存清单**——"用过一次之后才能离线用" |
| ONNX WASM 超平台上限 | 约 28MB > Cloudflare Pages 单文件 **25MB** | 无法随站点发布：`ort.env.wasm.wasmPaths` 指向 jsDelivr，并新增 `scripts/clean-onnx-wasm.mjs` 在构建后删除打进 `dist` 的副本 |
| 外部 CDN 可达性 | 两个 CDN 在国内均不保证 | 新增的**外部依赖风险**；且这不是可选优化，缺任一个 OCR 完全不可用 |

初始化超时为 `INIT_TIMEOUT_MS = 180_000`（180 秒），超时提示"首次使用需下载模型（约 10MB），请检查网络后重试"。

#### 3.3.2 数学公式：解析与渲染分两处

| 环节 | 定稿 | 说明 |
|---|---|---|
| 解析 | `remark-math@^6.0.0` | 支持 `$行内$` 与 `$$块级$$`；行内公式落在 `paragraph` 上并打 `hasInlineMath` 标记，块级产出独立 `math` 块 |
| 渲染 | `katex@^0.19.0` | `BlockRow.tsx`（3131 行）调 `katex.renderToString()`，区分 display / inline |
| Unicode 上下标 | `normalizeSuperSub()` | 扫描件输出的 `p²` 是 Unicode 字符而非 LaTeX，先映射成 `^` / `_` 再交给 KaTeX |

**`3d4a2ad` 修掉一个真实缺陷**：单行的 `$$...$$` 被 `remark-math` 解析成 `inlineMath`，于是**块级公式被当成行内公式渲染**（失去独立成行与居中）。修法是回查节点在原始文本中的偏移量，用源片段是否以 `$$` 首尾来判断——**判据必须来自原始文本，不能只看 AST 节点类型**。

> **已清理**：`rehype-katex@^7.0.1` 曾经装在依赖里但**源码从未 import**（公式没有走 rehype 管线，而是解析阶段产出 `math` 块、渲染阶段直接调 KaTeX）。本轮已把它连同 `pdf-lib`、`jszip` 一起从 `package.json` 移除，**依赖总数 29 → 26**（见 7.1）。

#### 3.3.3 公式 OCR：默认关闭的显式开关（C3 口径已收口）

通用 OCR 对公式输出乱码——源码注释里的实例是 `P{X=x,Y=y}=p²(1-p)^(x+y-2)` 被识别成 `PI{X=2,Y=y}=p"A−p""`。因此接入 SimpleTex 专用通道，**但它默认关闭**：

```
用户勾选「上传公式区域以换取更准的公式」→ formulaOcrEnabled = true（默认 false）
  → enhanceFormulaRegions()（词数 ≥3 才继续）
      第一道防线：开关关闭时在 detectFormulaRegions() 之前 return words
  → detectFormulaRegions()：置信度 < FORMULA_CONFIDENCE_THRESHOLD（70）即候选，
      ≥2 个相邻候选词聚成一个区域
  → 裁剪（四周留 10% padding）
  → formulaOcrService.recognizeFormula()（94 行）
      第二道防线：自己再查一次开关，关闭时抛错拒绝上传（不是静默返回空串）
  → Worker /api/formula-ocr → server.simpletex.cn
  → 整簇替换成单个词 text = '$' + latex + '$'，confidence 固定 95
```

| 环节 | 值 |
|---|---|
| **开关** | **`settingsStore.formulaOcrEnabled`，默认 `false`**；入口是 OCR 对话框的复选框「上传公式区域以换取更准的公式」。关闭时**不发起任何网络请求** |
| **第二道防线** | `recognizeFormula()` 自身检查开关，关闭时**抛错拒绝** —— 理由是「只靠调用方自觉不够，将来任何新调用方忘了检查就会静默把文档内容发出去」；检查早于 `await toPngBuffer(` 与 `await fetch(` |
| 触发门槛 | **开关打开且词数 ≥ 3** |
| 客户端上限 | `MAX_IMAGE_SIZE = 2_000_000` 字节 |
| 服务端上限 | **2,700,000** 个 base64 字符，超出返回 **413** |
| 密钥 | `SIMPLETEX_API_KEY`；缺失时返回 **500 `未配置 SIMPLETEX_API_KEY`**（线上实测当前就是 500） |
| 失败处理 | 只告警并**保留 PaddleOCR 的原始结果**（`公式增强失败（保留原始识别结果）`） |

> ✅ **这是本次同步最重要的一条口径变更，方向与上一轮相反。**
>
> 上一轮记录的是：公式 OCR **把页面局部像素自动上传到第三方 SimpleTex**，**不需要用户逐次确认**，界面上也没有开关 —— 与 C3「隐私是卖点：文档全程留在本机」**直接冲突**，状态为待决策。
>
> **现在已收口为默认关闭的显式 opt-in**：不勾选 → **一个字节都不外发、不发起任何网络请求**，默认路径恢复为「零上传」。
> 对外文案可以继续宣称"默认不把文档上传服务器"，**但必须同时说明**：一旦用户勾选该开关，页面局部像素会上传到第三方（经自建 Worker 转发）。
>
> **残余点（如实保留）**：勾选后需要联网、目的地仍是第三方 `server.simpletex.cn`、Worker 未配 `SIMPLETEX_API_KEY` 时该端点 500、
> 开关**没有**「哪些内容被上传过」的审计视图；且**真机行为未验证** —— 目前只有
> `src/store/formulaOcrPrivacy.test.ts`（**8 个用例**，其中 2 个专测第二道防线）与源码断言。

### 3.4 朗读与翻译

| 能力 | 定稿 | 关键取舍 |
|---|---|---|
| 朗读 | **双引擎 + 自动降级**：`CloudTTSEngine`（Azure 等，经自建代理） ↔ `BrowserTTSEngine`（Web Speech API） | 浏览器原生免费、离线、零配置，但音色取决于系统，且 Chrome 会在约 15 秒后静默中断长文本 —— 因此强制按 180 字切句朗读 |
| 翻译 | **代理模式**：DeepL / OpenAI 经 Cloudflare Worker 转发 | 密钥绝不能进前端。写在前端 = 公开 |
| 翻译策略 | **视口懒翻译 + 两级缓存** | 只翻可见区 ± 缓冲，并发上限 3；缓存键为 `hash(原文)+目标语言`，跨文档复用 |
| 降级路径 | 无密钥时 → 浏览器内置翻译 / 浏览器原生 TTS | 保证"零配置也能跑起来"，这是可交付性的底线 |

### 3.5 交互与性能

| 项 | 定稿 | 说明 |
|---|---|---|
| 虚拟滚动 | 自研（约 150 行） | 现成库普遍要求固定 `itemHeight`，而本项目的行高会随字号、行距、双语布局、译文展开变化。方案是"估算 + ResizeObserver 实测校正" |
| 批注锚定 | **偏移 + 前后 15 字指纹** 三级降级定位 | 只存 offset，文档一重新解析批注就会漂到别的句子上。失锚时**保留批注并标记**，不静默丢弃 |
| 选区渲染 | 边界点切分，不做字符串替换 | 批注会重叠；切分后拼接必须严格等于原文，否则界面丢字。已有单元测试守住这条不变量 |
| 主题 | CSS 变量 + `data-theme` | 三套主题只改一处变量，正文/译文/高亮全部跟随 |

## 四、实测数据（本仓库构建产物）

构建命令 `vite build`，实测结果：

| 产物 | 原始 | gzip | 何时加载 |
|---|---|---|---|
| `index.js`（应用主体） | 214 KB | **67.6 KB** | 首屏 |
| `vendor-react.js` | 219 KB | **68.3 KB** | 首屏 |
| `index.css` | 25.7 KB | **6.0 KB** | 首屏 |
| `vendor-text.js`（remark 全家桶） | 60 KB | 17.9 KB | 导入 md/txt 时 |
| `pdfParser.js`（pdfjs 主包） | 411 KB | 122.8 KB | **仅导入 PDF 时** |
| `pdf.worker.min.mjs` | 1.23 MB | — | **仅导入 PDF 时**（Worker 独立线程） |
| `epubParser.js`（epubjs） | 347 KB | 104.6 KB | **仅导入 EPUB 时** |

这个收益来自一个刻意的架构决定：解析器注册表把 PDF/EPUB 解析器改为**动态 `import()`**。若全部静态引入，首屏会变成约 380 KB gzip —— 而多数用户其实只读 md/txt。代价是查表变成异步，`parseFile()` 返回 Promise，这一点在对接时要注意。

## 五、明确不采用的技术及理由

写清楚"不做什么"和"做什么"同样重要，否则每个后来者都会重新讨论一遍。

| 不采用 | 理由 |
|---|---|
| Next.js / Remix / Nuxt | 解决的是服务端渲染与服务端数据获取问题，本项目没有服务端。引入后构建复杂度上升，收益为零 |
| 任何后端框架（Express / FastAPI） | 违反 C1、C3。没有需要服务端做的事 |
| 用户账号与云同步（本期） | 一旦有服务端就产生"文档在别人机器上"的隐私问题与合规成本。留作可选后续，且必须端到端加密 |
| 原生 IndexedDB 直写 | 回调 + 事务 + 游标的写法让代码量翻倍且极易出错 |
| 手写 EPUB 容器解析 | 见第二节，真实电子书的不合规情况远超预期 |
| `tesseract.js`（**已移除**） | 中文识别是长期弱项，且需手动选语言包。**已被 `ppu-paddle-ocr` + `onnxruntime-web` 取代**（见 3.3.1） |
| **自托管 ONNX Runtime WASM** | 约 28MB，**超过 Cloudflare Pages 单文件 25MB 上限**，物理上无法随站点发布 —— 不是取舍，是平台硬限制。改为运行时从 jsDelivr 加载 |
| **把公式当普通文本渲染** | 上下标与数学符号会全部丢失。改用 `remark-math` + KaTeX（见 3.3.2） |
| 现成虚拟滚动库 | 行高动态变化，配置成本高于自研 150 行 |
| 服务端 TTS 缓存 | 违反 C1；改为浏览器端 Blob 缓存 + IndexedDB 译文缓存 |
| Electron / Tauri 桌面版 | 浏览器已满足需求。真要桌面化，Tauri 比 Electron 更合适（体积小一个数量级），但那是下一阶段的事 |
| 自动 polyfill 服务（polyfill.io 类） | 供应链风险与额外网络依赖；本项目只需补两个 API，手写 30 行更可控 |

## 六、上线后修正的六个判断错误

以下六条不是设计阶段的推论，而是实测暴露出来后修正的。记在这里是因为它们都属于"当时看起来没问题"的典型误判。

### 6.1 pdf.js 5 依赖两个很新的 ES API，且补齐必须与它同处一个上下文

这是本项目最严重的一类缺陷，**连续踩了三次才彻底修好**，值得完整记录。

| API | 标准状态 | 缺失时的报错 | 触发路径 |
|---|---|---|---|
| `Uint8Array.prototype.toHex` | ES2025 提案 | `a.toHex is not a function` | 计算文档指纹 —— **每一份 PDF 都会走到** |
| `Promise.withResolvers` | ES2024 | 难以定位的 TypeError | pdf.js 内部广泛使用 |

**认知一：语法兼容 ≠ API 兼容。**
Vite 只做语法降级，不会为缺失的 API 注入 polyfill。代码能在 `es2022` 目标下编译通过，不代表运行时有这个函数。

**认知二：搜索范围要覆盖 worker 文件。**
`toHex` 只出现在 `pdf.worker.min.mjs` 里，主包一处都没有。"检查主包是否可用"的验证会漏掉它 —— 第一次修复只补了 `withResolvers` 就是因此。

**认知三（最关键，也是第三次才想通的）：polyfill 只对执行它的那个 JS 上下文有效。**
Web Worker 拥有独立的全局对象与原型链。主线程对 `Uint8Array.prototype` 打的补丁，**worker 内部完全看不到**；而 `toHex` 恰恰只在 worker 里被调用。

这解释了一个诡异现象：**本地测试全绿，线上照旧报错**。因为 Node 25 原生就有 `toHex`，主线程也有补丁 —— 两边都有，唯独真正需要它的那个 worker 没有。前两次"修复"之所以无效，是因为验证方式本身就在错误的环境里。

**最终修复（第四次尝试才成功）**：不再试图改 pdf.js 的行为，而是**提供自己的 Worker 入口，把补齐放在 pdf.js 之前**。

新增 `src/parsers/pdfWorkerEntry.ts`：

```ts
// ⚠️ 顺序不可调整：补齐必须在 pdf.js 的 worker 代码之前执行
import '@/lib/polyfills';
import 'pdfjs-dist/build/pdf.worker.min.mjs';
```

主线程用 `PDFWorker.create({ port })` 传入这个 Worker 实例（`src/parsers/pdfRuntime.ts`）。**import 顺序即执行顺序**，结构上不可能出错，同时保留了 Worker 的性能优势。

期间否决的方案及原因：

| 方案 | 否决原因 |
|---|---|
| 只在主线程补 API | worker 有独立原型链，看不到补丁 —— 这就是前三次失败的原因 |
| 让 pdf.js 跑主线程（不设 `workerSrc`） | pdf.js 5 **不会**自动退回主线程，而是直接抛 `No "GlobalWorkerOptions.workerSrc" specified` |
| 把 `workerSrc` 指向 pdf.js 自带的 worker 文件 | 那个文件内部没有补齐，依然在 worker 里报 `toHex` |
| 往 pdf.js 内部注入补丁 | 依赖内部模块结构，跨版本极易失效，且失败是静默的 |

- 代价：Worker 资产 1.15 MB，首次导入 PDF 时加载（之后全局复用）。
- 验证：构建产物中 `pdfWorkerEntry-*.js` 必须同时含补齐模块与 pdf.js 代码，且**补齐的字节偏移在前**。
- **防线**：`src/parsers/legacyBrowser.test.ts`，**主动删掉原型上的 `toHex` 来模拟旧浏览器**，再跑完整解析。这把"本地永远复现不出来的线上问题"变成了必然失败的测试。

门槛：**Chrome / Edge 119+、Firefox 121+、Safari 17.4+**。

一个反直觉的细节：Node 25 已原生支持这些 API，**但语义与提案不同**（原生 `fromHex` 不跳过空白、`fromBase64` 需显式指定字母表）。所以"运行时支持"不等于"语义一致"，测试必须直接验证我们自己的实现。

### 6.2 为一个错误类拖进整棵依赖树（首屏包 68KB → 201KB）

扫描件识别需要在 `parsers/index.ts` 与 `store/libraryStore.ts` 中判断"这是不是扫描件"。最自然的写法是 `import { ScannedPdfError } from '@/parsers/pdfParser'` —— 但这一个 import 会让首屏包**静态引入 pdfjs（415KB）以及当时的 OCR 引擎 `tesseract.js`**，主包 gzip 从 68KB 涨到 201KB。按需加载的优化被一行 import 抵消。

> **时效说明（本次同步）**：这两个数字（415KB / 68KB→201KB）是 `tesseract.js` 时代实测的，此后 OCR 引擎已换成 PaddleOCR（`cdf2957`）。**结论不变**（重量级实现必须按需加载），但具体体积未复测。

- 对策：把错误类型与语言常量抽成零依赖模块（`parsers/scannedPdfError.ts`、`lib/ocrTypes.ts`），重型实现（`pdfParser.ts`、`lib/ocrEngine.ts`）再重新导出它们，保持既有调用路径可用。
- 判据：**跨模块共享的常量与类型，必须与重量级实现分离。**
- 附带修正：`ocrEngine` 改为在 `ocrParsePdf` 内部动态 `import()` —— 只有真的执行 OCR 时才下载 OCR 引擎。**这条至今有效，而且更重要了**：现在按需加载的是 PaddleOCR + ONNX Runtime WASM（约 28MB）。
- 类型守卫改用标记属性而非 `instanceof`：pdfParser 是动态 import 的，跨模块实例判断用结构特性更可靠。
- **验证方式：不只看源码，看构建产物。** `dist/assets` 里应存在独立的 `pdfParser-*.js` 与 `ocrEngine-*.js`，且入口 chunk 不含 pdfjs 特征串。源码看起来对不代表打包结果对。

### 6.3 PDF 断段阈值必须自适应，不能用固定倍数

初版按"行距 > 1.0 × 字号即断段"实现。实测一本 12pt、1.2 倍行距的 PDF，行距约 14.4pt，而字号也是 12 —— 14.4 > 12 恒成立，**每一行都被切成独立段落**，整篇文档碎成上千块。

- 对策：两遍扫描。先求本页相邻行距的**中位数**（即这本书的正常行距），再据此判定：超过中位数 1.35 倍、或字号突变、或上一行已结句且留白不小于中位数（×0.95），才断段。
- 为什么末条用 0.95 而不是大于 1：整篇行距完全均匀的 PDF 里没有任何"行距变大"的信号，此时"上一行已结句"是唯一可用的断段依据。

### 6.4 `File.text()` 一律按 UTF-8 解码，中文 txt 会读成空白/乱码

浏览器原生 `File.text()` 固定按 UTF-8 解码。而中文 Windows 导出的 `.txt` 有相当比例是 **GBK/ANSI**，记事本另存的"Unicode"则是 **UTF-16LE**。

- 现象：文件"打开了但内容是空的"或满屏乱码。
- 对策：`src/lib/textEncoding.ts` 三级识别 —— BOM 嗅探 → 按 UTF-8 解码并统计替换字符比例（U+FFFD 是强信号）→ 回退 GB18030（GBK 超集）。识别结果写进文档标签，用户可自查。

### 6.5 解析出 0 个块不能静默通过，且必须区分成因

静默返回空文档是体验最差的失败方式：用户看到"导入成功"却一片空白，既不知道哪里错，也无从排查。但仅"报错"不够 —— 成因不同，处置办法完全不同：

| 情况 | 判定方式 | 处置 |
|---|---|---|
| 整本无文字层（扫描件） | 有文字的页数 = 0 | 抛 `ScannedPdfError`，界面提供浏览器端 OCR 入口 |
| 少数页无文字（封面/插图） | 有文字的页数 < 30% | **不阻断导入**，控制台说明跳过页数 |
| 其余格式解析出 0 块 | `parseFile` 兜底校验 | 报错并提示可能是空文件或二进制内容 |

诊断这类问题需区分"页面里没画东西"和"我们没看到画的东西"。pdf.js 的 `getOperatorList()` **默认不展开 Form XObject 内部的指令**，而扫描件恰恰是把图片放在 Form XObject 里再用 `/Im0 Do` 绘制的 —— 用默认参数会得出"页面是空的"这一**错误结论**。必须传 `intent: 'display'`。（这个坑我踩过一次，`scripts/diagnose-pdf.mjs` 里已标注。）

### 6.6 一次被误诊的 PWA 故障，以及一剂副作用未消的药

这是本项目最难定位的一次线上故障，也是**唯一一次"修了但方向错了"**的记录。

**现象**：导入 PDF 时报 `Failed to fetch dynamically imported module: .../pdfParser-CiRxJgol.js`。页面正常、md/txt 正常，**只有按需加载的解析器炸**——因为 md/txt 的 chunk 在入口依赖图里，pdf/epub/ocr 是动态 `import()`。

**真因**：`vite.config.ts` 里的 `navigateFallback: '/index.html'` 注册了一条 `NavigationRoute`，**直接返回预缓存里的旧 HTML，不经过网络**。旧 HTML 引用旧构建的 chunk 哈希，而新部署后那些文件已被删除 → 动态 import 一个不存在的文件。

**证据（读源码，不是推测）**：`workbox-build@7.4.1` 的 `build/templates/sw-template.js` 第 52–58 行显示，`navigateFallback` 生成的 `NavigationRoute` 注册在 `runtimeCaching` 各路由**之前**（52 行是 `NavigationRoute`，58 行才 `runtimeCaching.forEach`）；Workbox **按注册顺序匹配路由**——所以只要设了它，导航请求永远命中预缓存。

**`d7a5bae` 开错了药**：它把 `registerType: 'prompt' → 'autoUpdate'`、`skipWaiting: false → true`。但 `skipWaiting` 管的是「新 SW 何时接管」，**管不了「已经接管的 SW 主动把旧 HTML 递给用户」**。

**正确修法（`a766d3f`）**：`navigateFallback: undefined`，改为显式导航路由 `request.mode === 'navigate'` → `NetworkFirst`（`cacheName: 'html-navigation'`、`networkTimeoutSeconds: 3`、`maxEntries: 8`、`statuses: [0, 200]`）——**在线拿最新 HTML，离线回退缓存**。另加 `src/lib/preloadRecovery.ts`（152 行）监听 `vite:preloadError` 自愈。

**`aa8827a` 补上 NetworkFirst 的新空档**：该缓存只在「SW 接管之后的第一次导航」才写入，于是"首次访问 → 立刻断网 → 打开已安装应用"会白屏。修法是 `src/lib/pwaOffline.ts`（60 行）在 `onRegisteredSW` 时趁在线 `fetch('/')` 并 `cache.put('/')`。**不能退回 `navigateFallback` 来解决离线——那会重新引入本次修复的 bug，两者互斥。**

#### 6.6.1 `autoUpdate` 的副作用：已决策（保留 + 删掉永不触发的死 UI）

读 `vite-plugin-pwa@1.3.0/dist/client/build/react.js` 可确认：`autoUpdate` 模式下编译期常量 `auto === true`，于是

1. `updateServiceWorker()` 的函数体是 `if (!auto) { sendSkipWaitingMessage?.() }` → **它是个空操作**；
2. `onNeedRefresh` 只在 prompt 分支被调用 → **`needRefresh` 永远为 false**，`PwaPrompt.tsx` 的"有新版本可用 / 立即更新"提示条**永远不会出现**；
3. `activated` 事件在 `event.isUpdate` 为真时 `window.location.reload()` → **页面会自动重载**。

> **状态：已决策（本轮落地）。** 三者都按「保留 `autoUpdate`」处置：
> 第 1、2 条对应的代码是**死代码，已删除** —— `PwaState` 从 `{ needRefresh, offlineReady, update, dismiss }`
> 收窄为 **`{ offlineReady, dismiss }`**，删掉 `updateServiceWorker` 解构与 `update()`，
> 并删除 `PwaPrompt.tsx` 的「有新版本可用 / 立即更新」分支与 `RefreshCw` 图标
> （`Banner` 的 `tone` 由 `'update' | 'offline' | 'ready'` 收窄为 **`'offline' | 'ready'`**）；
> 第 3 条是决策本身接受的**代价**。
>
> **代价必须写清**：页面会在**无预警**的情况下自动重载，**滚动位置、展开的译文、正在进行的 OCR 都会丢**。
> `src/lib/pwa.ts` 原先把这段代价写成了"所以要选 prompt"，那段注释已**整段重写**为记录 autoUpdate 决策
> （含代价与理由），**代码注释与配置不再互相矛盾**。
>
> ⚠️ **其中「正在进行的 OCR 会丢」这一项已经真实发生过，并已单独缓解**（提交 `fc79896`）：
> 用户在一次扫描途中遇到部署上线 → 页面自动重载 → 整次 OCR 结果随内存一起消失，
> **且没有任何报错**（状态本就随刷新清空）。根因是三件事叠加：SW 无预警重载、
> `libraryStore` 刻意不持久化、`startOcr` 只在最后一页跑完后才写库。
> 现在：**导入/OCR 期间推迟刷新**（`onNeedReload` 里判断 `libraryStore.importing`）
> 且**每 5 页中途落盘一次**。丢失窗口从「整次扫描」降到「最多几页」。
> **注意：这缓解的是「进行中的 OCR 全丢」，不改变「页面仍会自动刷新」这一事实** ——
> 滚动位置与展开的译文仍会丢。详见 `03-踩坑与修复记录.md` 缺陷 21 与 `06-PWA离线能力.md`。
>
> **本轮之后**：`onNeedReload` 已不再是「将来可用」的备选，而是**已经在用**（见上）。
> `PwaState` 因此新增 `updatePending` 与 `reloadNow` 两个成员。
>
> `vite.config.ts` 至今**未改动**，仍是 `registerType: 'autoUpdate'` + `clientsClaim: true` + `skipWaiting: true`。

**本次同步的实测证据**（本轮）：`npx tsc -b` exit 0；`npx vitest run` **200 passed / 18 files**（上一轮 205 / 18）；`npm run build` 得到 `precache 18 entries (3578.54 KiB)`，`[verify-dist]` 报产物共 **83 个文件，5.54 MB**、WASM 解码器 **7 个合计 1.41 MB**；`src/` 规模为 **63 个文件 / 10,636 行**。线上 `sw.js` 含 `NetworkFirst` 与 `html-navigation`，**不含** `createHandlerBoundToURL` → 修复确已上线（上一轮实测，本轮未复测）。

**一条必须记住的教训：本地构建哈希 ≠ 线上构建哈希。** 本轮本地 `index-BBM5E4Bw.js` / 线上（`f549173`）`index-BUj-R2J2.js`；本地 `pdfParser-DJvvPlRl.js` / 线上 `pdfParser-BjFMW2CJ.js`。Cloudflare 的构建**不是逐字节可复现的**——**绝不能用本地 `dist/` 里的文件名去推断线上资源名。** 另外本轮改动**已部署**（`f549173`）。
