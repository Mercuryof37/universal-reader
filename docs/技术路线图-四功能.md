**同一个病第二次发作。** 修法是特性检测 + 明确的降级文案，半小时级。

### 2.2 项目有 3 条外发路径，只有 1 条是 opt-in（`02` §五）

## 三、我的排序（与两份子文档的建议不完全一致）

两份文档各自选了一条"最值得先做"。**我不完全同意它们的顺序**，理由如下。

### 第 0 位：2.1（Firefox 翻译死路）+ 2.2（外发路径告知）

`02` 建议把 Firefox 那条当"顺手做掉的小修"。**我把它提到最前**，因为：

- 它影响的是**用户正在用的浏览器**，且**错误条刷屏、没有出路**；
- 它是**同一个病的第二次发作**——不修，就会有第三次；
- 2.2 是**产品口径问题**，manifest 里那句"不上传服务器"现在**与代码事实不符**，
  这比任何功能缺失都严重。

### 第 1 位：`01` P0-1「只导出数据，不改判据」

在 `chars[]` 里加 `inkHeight` / `pageMaxHeight` / `heightRatio`。

**我完全同意这一条排在最前**，而且理由比文档里写的更强：

> 机制 5 **已经算出**指数的比值（`x` = 0.35、`2` = 0.54，都 < 0.8），
> **它们只是被置信度门挡在前面。**

也就是说**答案是已知的，缺的只是"能看见"**。而这正是这一轮里
**同一个错误发作了三次**的那个东西——用一个未经验证的假设去验证另一个假设。
三次都是靠**把看不见却决定结论的量变成字段**走出来的：

```
charBoxSkips  →  charConfidencesComplete  →  chars[].confidence
```

**第四次不该再靠运气想起来。** 体积 +0、依赖 +0、风险 0。

### 第 2 位：`02` P0-1「把暂停做成暂停」

`ReaderView.tsx:252` 的 `aria-label="暂停朗读"` **在说谎**——
按下去走的是 `speechSynthesis.cancel()`（`ttsEngine.ts:140`），语义是**取消并丢弃**，
一段 800 字的正文会**从段首重读**。

改动封闭在两个文件里，零依赖、零联网、零体积，**每个按过的用户都会立刻感知**。

### 第 3 位：`01` 四·P0-1 文字层 PDF 的页眉页脚过滤

唯一一条「**用户每天都会遇到、现在 100% 会发生**」的排版缺陷——
300 页书产生近千碎片，**直接毁掉 TTS 朗读顺序**。纯计算、体积 +0、可回退。

### 顺带

`02` P0-3（`sentenceSplit.ts` 中文断句）建议与第 2 位同迭代——
纯函数、可单测，是句级高亮的前置，**且 TTS 与翻译共用**。

## 四、我不建议做的（以及为什么）

| | 理由 |
|---|---|
| **浏览器内离线 NMT** | 最小可行模型 int8 后单文件仍 50 MiB+，全部超限且必须走第三方 CDN |
| **公式 OCR 模型** | 最小 224 MB，超限 9 倍。现有启发式是唯一可行路径 |
| **UVDoc 去扭曲** | 30.3 MB，超限 118% |
| **`piper-wasm`** | 解包 **224.60 MiB**（反面教材）；且 espeak-ng 音素数据体积**未核实**，是 Piper 方案的**关键未知** |
| **句级高亮覆盖 Markdown** | 要动 `BlockRow`/`RichText` 两条渲染路径，风险高；先只对 `md === false`（PDF/TXT/OCR 来源）启用 |

## 三、OCR 功能路线

> **排序依据 = 用户可感知的收益 ÷ 实现风险。** 不按技术炫技程度排。
> 每条格式统一：**问题 → 做法（含具体文件/模型/体积/依赖）→ 参照 → 验收标准 → 风险**。

### P0-1 · 把「机制 5 可以独立成立」做完，让指数 `x+y−2` 真正判出来

**问题**
误判已经归零（真实导出 `buildId 2026-10-08T10:48:02.355Z`：误判 0、真阳性 2），
但**含指数的词仍然拿不到 `^{…}`**。原因**可算、无争议**【HANDOFF 记载】：
指数五字符置信度 `0.9953 / 0.9997 / 0.9205 / 0.957 / 0.9883` 与必须拒绝的字符（`P` 0.9877、`=` 0.9965–0.9984、`Y` 0.9892）**重叠**，
所以**机制 2（`SCRIPT_WORSE_CERTAINTY = 0.93`）先把整个指数拒掉了**。
而**机制 5 其实已经算出** `x` 高度比 **0.35**、`2` 高度比 **0.54**（都 < `SCRIPT_MECH5_SCALEDOWN_RATIO = 0.8`）——
**它们只是永远轮不到被用**。

**做法（分两步，第 1 步不做完不许做第 2 步）**

1. **先把那个决定结论的量变成字段**（这是本项目自己总结出的第六条元教训，
   三次都靠这个动作走出来 —— 【HANDOFF】§5.13.12）：
   在 `src/lib/ocrStructure.ts` 的 `chars[]` 里，与现有 `confidence`、`bbox` 并列，
   **加上机制 5 的两个数**：`inkHeight`（`h`，像素）与 `pageMaxHeight`（`H(c)`，像素），
   以及派生出来的 `heightRatio = h / H(c)`。
   - 数据来源现成：`ocrCharBoxes.ts:1225` `buildCharSizeTable()` 已经产出 `H(c)`；
     `h` 来自 `measureCharPixelSpans()`（`:564`）。
   - **不新增任何依赖、不新增任何模型、体积 +0**。
   - 判据侧不要改任何阈值 —— 这一步**只导出，不判定**。
2. **再改判据**，让机制 5 的结论可以**独立成立**：
   在 `ocrCharBoxes.ts` 的 `classifyCharsByGeometry()`（`:1550`）里，
   把「几何合格 **且** 尺寸比 < 0.8」当作一条**独立的通过条件**，不再强制要求低置信度。
3. ⚠️ **动手前必须先产出两份名单并求交集为空**（【HANDOFF】R10 把这条写成**硬要求**，不是建议）：
   - **会被放行的名单**：把整页所有几何合格的字符逐个过一遍新条件，列出来；
   - **必须拒绝的名单**：`P` / `=` / `∼` / `√` / `Y`。
   交集必须为空。**只凭"测试变绿"不算验收。**
4. 已知缺口要一并承认：机制 5 **单独会丢掉指数里的 `+` / `−`**（它们在本页只有缩小形态 → `H` 就是它自己 → 比值 1.0 → 被拒）。
   **正确方向是"页面上真的存在全尺寸的 `+`/`−`"，不是放宽阈值。**

**参照**：Tesseract `ccmain/superscript.cpp` 机制 5（用字体度量表做分母）；
本项目的替代（用本页实测最大高度）已在 `SCRIPT_MECH5_SCALEDOWN_RATIO` 的注释里写明**四处刻意偏离**与依据。

**验收标准**
- 真实扫描件导出里，含指数的那一行出现 `^{…}`；
- **误判数保持 0**（不得从 0 变回 1）；
- `charBoxSkips` 里剩下的**全是认错字**；
- **并且**能出示「会被放行的名单 ∩ 必须拒绝的名单 = ∅」这一份独立证据。

**风险**
- **中高**。这一条**改的是判据本身**，而【HANDOFF】§5.11.5 明确记过"改判据回归风险大"。
- 历史证据：这条线**已经因为"改了没验证"白走过两轮**（§5.13.5 的错误结论、§5.13.7 的三处"全有或全无"）。
  第 3 步的名单就是为这两轮付的学费。
- 紧边必须知道：实测最紧的一个数是 `=` 的墨迹高 **7.3**；若与第 1 词同页，
  同一个 `6.1` 的 `=` 比值就是 **0.836**，**离 0.8 只剩 0.036**。
  **不要把 `SCRIPT_MECH5_SCALEDOWN_RATIO` 降到 0.72 以下"求稳"** —— 那会把"被缩小得不多"的真上标一起放进来。

### P1-1 · 让版面的"剔除决策"变得可审计

**问题**
版面模型参与**阅读顺序与页眉页脚**判定，逐字节回退不变量只保证"模型缺席时不坏"，
**不保证"模型在场且判错时不坏"**。而【HANDOFF】§7 把这一条列为 **P0 / 难度"高"**，
原话是「等于把一个未验证的组件放进了正文链路」。
现在用户能看到的只有控制台里的一行 `[layoutAnalysis] 版面区域 N 个（其中页面家具 M 个：header×1、footer×1…）` ——
**看不到"被剔掉的具体是哪几行字"**。

**做法**
1. 把被版面模型判定为 `header` / `footer` / `number`（`LAYOUT_LABELS` 的 13 / 15 / 3，🟢 `layoutAnalysis.ts:115`）
   **并且真的被丢弃**的**文本内容**，记进 `ocrStructure` 导出
   （新增字段，例如 `layoutFurniture: { label, text, bbox }[]`），与 `charBoxSkips` 同一层。
2. 复用**已有的三条安全设计**（🟢 `layoutAnalysis.ts` + 【HANDOFF】§5.11.5）：
   `analyzePageLayout()` 任何失败返回 `null`、失败缓存为"本会话不可用"、
   逃生开关 `VITE_OCR_LAYOUT=0`。**新增的只有"导出"这一件事。**
3. **不要**在这一步加用户界面开关 —— 先把数据拿出来。

**参照**：本项目 `charBoxSkips` 的成功经验（【HANDOFF】§5.12.7：加上它之后"一眼看清"，
一次否掉了"WebGPU"与"词太宽"两个猜测）。

**验收标准**
- 一份真实导出的 JSON 里，能**逐条列出**"这一页被当成页眉/页脚丢掉的每一段文字及其 bbox"；
- 人眼比对：**丢弃的应当都是页面家具**；若有正文被丢，能**直接看到是哪一句**（而不是靠猜）。
- 不改变任何现有输出（新增字段是纯增量）。

**风险**
- **低**。纯增量字段，不改判据。
- 唯一要注意的是**导出体积**：`ocrStructure.ts` 的头注释已说明它**刻意控制体积**。
  家具条目通常每页 1–3 条，可忽略；但应在实现时**只导出被丢弃的**，不要导出全部区域。

### P1-2 · 用几何投影做双栏检测与阅读顺序，先落地"保守退回单栏"

**问题**
教材、论文的左右栏被读成一行，**正文顺序完全错乱**（【HANDOFF】§7 P0 表）。
而且这一条**在 OCR 路径上也没有解决** —— `PP-DocLayout-S` **只给区域 + 类别，不给顺序**
（🌐 官方 `layout_analysis` 文档明确：顺序是 `PP-DocLayoutV2` 那个**级联指针网络**的职责，
而 V2 是 **203.8 MB = 25 MiB 的 814%**，📕 与【HANDOFF】记的 203.42 MiB 一致）。

**做法（零新依赖、零新模型、体积 +0）**
1. **加一个"栏检测"模块**（例如 `src/lib/ocrColumns.ts`），输入是行/词的 x 区间集合，做法：
   - 在版心宽度上做 **x 投影直方图**（每列像素或词数），找**近似全高的空白带**（gutter）；
   - **gutter 判据要保守**：空白带宽度需 ≥ 若干倍主字号，且**不得**落在任何 `formula` / `table` / `figure` 区域内。
2. **阅读顺序用递归 XY-Cut**，并按 **XY-Cut++ 的三个改进点**去做（🌐 arXiv:2504.10258）：
   - **pre-mask**：**先用已有的版面类别把不该参与切割的元素遮掉**
     （`figure` / `table` / `header` / `footer` / `page_number` 不参与切分，切完再按位置插回）。
     **这正是本项目相对于"裸 XY-Cut"的天然优势** —— 类别已经有了。
   - **多粒度**：先在"页 → 栏 → 块"粗粒度切，再在块内按行切；不要在词一级递归。
   - **跨模态**：用文字语义辅助（例如跨栏的整行标题、`paragraph_title` 区域）避免把标题切进某一栏。
3. **必须有"不确定时退回单栏"的保守策略**，并且**退回是默认**：
   判定不出 gutter、或切完每一栏的行数分布明显不均（例如某栏只有 1 行）→ **不切**，
   行为与现在**逐字节相同**（照抄 `layoutAnalysis` 那条"回退不变量 + 测试锁第一组用例"的做法）。
4. **Tesseract 的 PSM 4「Assume a single column of text」**（🌐 官方 `ImproveQuality` 页的 PSM 列表）
   可以作为**第二意见**：本项目已经有 tesseract.js 支路（`ocrTesseractScripts.ts`），
   在**分栏不确定**时按栏各跑一次单列几何，与主链路的栏划分对账。

**参照**
- **XY-Cut++**（🌐 https://arxiv.org/abs/2504.10258）：pre-mask + 多粒度 + 跨模态，整体 98.8 BLEU、最高超基线 24%。
- **PP-DocLayoutV2** 的"检测 → 指针网络 → N×N 相对顺序 → 胜者累积"（🌐 官方 `layout_analysis` 文档）：
  **不需要抄模型，抄"先有 N×N 成对关系再解码成拓扑序"这个结构** —— 几何投影给出的"上下/左右"关系，
  本质上就是一个稀疏的 N×N 关系矩阵。

**验收标准**
- 准备**单栏与双栏各 ≥2 份真实样本**（【HANDOFF】R3 已把这条列为前置）；
- 双栏样本：正文顺序正确（人工核对整页文字流）；
- **单栏样本：输出与接入前逐字节相同**（这是硬要求，不是"差不多"）；
- 用 `scripts/inspect-pdf.mjs` 已有的"断段是否过碎/过粗"指标做前后对照（🟢 该脚本已在仓库里）。

**风险**
- **中**。判定错误**会让单栏文档变得更糟** —— 这是【HANDOFF】R3 自己写下的风险。
- 缓解：**退回是默认**、**测试锁逐字节不变量**、**两份单栏样本是准入门槛**。
- **体积影响：0**（纯几何 + 纯 TS）。

### P2-1 · 评估把裸 `onnxruntime-web` alias 到 `onnxruntime-web/wasm`（−13.4 MB 流量）

**问题**
🟢 **实测读源码**：`src/lib/ocrEngine.ts:63` 是
`ort.env.wasm.wasmPaths = 'https://cdn.jsdelivr.net/npm/onnxruntime-web@<version>/dist/'`，
而三处裸标识符 `import * as ort from 'onnxruntime-web'`（`ocrEngine.ts:10`、`ocrCharBoxes.ts:88`、
以及 `ppu-paddle-ocr` 内部）在 `onnxruntime-web@1.30.0` 的 `exports` 里落到**全 EP 包**，
对应的 wasm 是 `ort-wasm-simd-threaded.jsep.wasm` = **27.00 MiB**；
而该包**确实提供**只含 wasm EP 的入口 `./wasm` → `ort-wasm-simd-threaded.wasm` = **13.58 MiB**。
`docs/字符级OCR技术调研.md` §6.6 把这一条标为"本次调研里最可执行的发现之一"，但**未实测**。

**做法**
1. 用 Vite `resolve.alias` 把裸标识符 `onnxruntime-web` 指到 `onnxruntime-web/wasm`，
   让三处 import **一并**落到 wasm-only 包。
2. **前置条件（必须同时满足）**：本项目**坚持 `executionProviders: ['wasm']`**。
   🟢 实测 `src/lib/ocrExecutionProvider.ts:38`：默认返回 `['wasm']`；只有 `VITE_OCR_USE_WEBGPU=1` 时才返回
   `['webgpu','wasm']` —— 而 **wasm-only 包里没有 WebGPU EP**。
   所以这个 alias **必须与"不用 WebGPU"这个既有决策绑在一起**（【HANDOFF】缺陷 22：
   WebGPU 会加载 27 MB 的 jsep 且**实测出现过页面被回收**）。
   **建议：alias 生效时，让 `VITE_OCR_USE_WEBGPU=1` 直接报错或警告**，避免两件事脱节。
3. ⚠️ **必须真机验证**：alias 会同时改写 `ppu-paddle-ocr` 内部的裸 import
   （Vite 对裸标识符的标准行为），**但没有验证过它不破坏库的会话创建**。

**参照**：`docs/字符级OCR技术调研.md` §6.6（证据链最完整的一条，但作者自己标注"仍未实测"）。

**验收标准**
- 真机跑一次完整 OCR（前 10 页），**成功**；
- DevTools Network 里确认加载的是 `ort-wasm-simd-threaded.wasm`（**13.58 MiB**）
  而**不是** `...jsep.wasm`（27.00 MiB）；
- `npm run build` 的 `scripts/verify-dist.mjs` 仍然通过
  （🟢 该脚本对产物**每个文件统一复查 25 MiB 上限**，`MAX_ASSET_BYTES = 25 * 1024 * 1024`）。

**风险**
- **中**。收益明确（**−13.4 MiB 首屏流量，约减半**），但**一次真机验证是硬门槛**。
- 与 25 MiB 的关系：**这一条不涉及站点资产**（wasm 来自 jsDelivr，不是 Pages 资产），
  所以它**不受 25 MiB 约束**，纯粹是用户流量与"首次可用时间"。
- 附带风险：`VITE_OCR_USE_WEBGPU=1` 会失效 → 必须显式处理，不能静默。

### P2-2 · 把"方向分类"和"更大版面模型"作为两个可评估的候选（**先把体积量出来再决定**）

**问题**
两个真实的、互不相关的缺口：
(a) **手机拍摄的页面被旋转 90°/180°** —— 现有链路会整页失败，且**用户在导出里看不出原因**；
(b) 在用的 `PP-DocLayout-S` 官方 mAP(0.5) 只有 **70.9**，而**同一张官方表里 `PP-DocLayout-M` 是 75.2**。

**做法（这一条的第一步是"量体积"，不是"接模型"）**
1. **(a) 方向分类**：候选 `PP-LCNet_x1_0_doc_ori`，🌐 官方标称 **7 MB**（Top-1 Acc 99.06%，
   4 类 0°/90°/180°/270°）。
   - **7 MB ≈ 6.68 MiB = 25 MiB 上限的 26.7%** → **单文件合规**。
   - ⚠️ **但它只有 Paddle 推理格式**，需要 `paddle2onnx` 转换，**ONNX 导出件的真实字节数 📕 未核实**。
   - **必须先做**：`Get-ChildItem` 量出真实字节数，再决定是否接入。
   - 接入形态：**懒加载**（与 tesseract 第二意见同一套做法：同源、运行时 CacheFirst、
     不进 precache 清单）。方向判定应在**整页 OCR 之前**跑一次，代价 3.24 ms/页（官方 CPU 数字）。
2. **(b) 更大版面模型**：候选 `PP-DocLayout-M`，🌐 官方标称 **22.578 MB**
   （mAP 75.2 vs `PP-DocLayout-S` 的 70.9）。
   - **22.578 MB ≈ 21.53 MiB = 25 MiB 上限的 90.3%** → **单文件合规，但只剩 2.4 MiB 余量**。
   - ⚠️ 同样是 Paddle 格式，**ONNX 后字节数 📕 未核实**。**`PP-DocLayout-S` 的官方 4.834 MB
     对应本机 ONNX 4,917,852 字节（4.69 MiB）** —— 这个 +1.7% 的实例说明
     "ONNX 与 Paddle 体积极接近"，**但不能据此推断 M 版一定合规**，必须实测。
   - **只有在前一条"版面精度评估"（P1-1 的导出 + 人工核对）已经能给出可比数字之后**，
     换模型才有意义 —— **否则换了也不知道是变好还是变坏**。

**参照**：🌐 https://www.paddleocr.ai/main/version3.x/module_usage/layout_detection.html （官方模型表）、
🌐 https://www.paddleocr.ai/main/version3.x/module_usage/doc_img_orientation_classification.html

**验收标准**
- 第一步（体积）：**给出两个 ONNX 文件的真实字节数**（`Get-ChildItem`），并明确写出占 25 MiB 的百分比；
  **若任一转出件 > 25 MiB，立即停止，不做**（这正是 `PP-DocLayoutV2` 被否掉的方式）。
- 第二步（功能）：方向分类——`90°` / `180°` 两个真实样本能被纠正后识别成功；
  版面模型——**同一批真实页面**上，新旧模型的"页面家具误剔/漏剔"计数对比可出示。

**风险**
- **低到中**。两者都是**加一个懒加载模型**，**主链路逐字节不变**（照抄"模型缺席即回退"的设计）。
- 主要风险是**体积未核实就动手**（`PP-DocLayoutV2` 就是这么被浪费掉的）。
- 与 25 MiB 的关系必须写进出入口：**`PP-DocLayout-M` 的 90.3% 占用率意味着它之后，
  25 MiB 这条预算基本用尽** —— 再想加模型就只能替换、不能叠加。

🟢 【HANDOFF】§5.12.3 记载：字符级解码的**唯一一次真实模型验证**（`ABC123` / `HELLO` / `X7` / `WELCOME`

**验收标准**
- 一个命令能跑出四个字符串的正确解出结果；失败时**明确报"前处理与库脱节"**，

**风险**
- **低**。纯粹补测试/脚本，不改产物。
- 唯一成本是**要在能跑真实模型的环境里执行一次**。

## 四、页面排版路线

> 与第三节同格式。**排版这条线的总原则**：本项目已经**换了三次方法**
> （几何启发式 → 版面模型 → 版面模型 + 几何），每次换法都在打同一批边界情况。
> 因此这一节的排序里，**"让现状可审计" 优先于 "再换一次方法"**。

### P0-1 · 文字层 PDF 的页眉页脚过滤（**当前最大的确定性缺口**）

**问题**
🟢 **本机实测**：`filterHeaderFooter()` 与 `applyLayoutToLines()` **只作用于 OCR 路径**。
走**文字层**的普通 PDF（`parsers/pdfParser.ts`）**没有任何等价过滤**。
后果【HANDOFF】§7 P0 表原话：一本 300 页的书会产生**近千个碎片**，
污染阅读流与朗读顺序 —— 而**朗读顺序错了，TTS 就整段报废**。

**做法**
1. **不要在新路径上重写一套判据。** 先看能不能**复用版面模型的输出**：
   `PP-DocLayout-S` 是**对页面图像**做推理的（输入 `[N,3,480,480]`），
   而文字层 PDF **可以渲染成页面图像**（`pdfjs-dist` 已在树里、`scripts/copy-pdfjs-wasm.mjs` 已把解码器放好）。
   - 代价：**每页一次 480×480 的版面推理** + 一次渲染。**体积 +0**（模型已在同源）。
   - ⚠️ 但**文字层 PDF 渲染成图是纯浪费**（它本来就有坐标），**要评估是否值得**。
2. **更省的替代**：文字层 PDF 的词框**直接可得且精确**，所以走**跨页重复统计**（【HANDOFF】R2 原方案）：
   - 统计"出现在页面顶端/底端固定 y 区间"**且跨页高度重复**的文本；
   - 判据要点（必须写死）：**位置归一化后**的 y 区间（不是绝对像素）、
     需要 **≥ N 页重复**才认（建议 N ≥ 3，单页命中不算）、
     且**不含正文高频词**（否则会把"第 1 章"这类真实标题吃掉）。
   - 命中的行**不进正文，但记进 `metadata` 供回跳**（不删数据）。
3. **两种都做，但先做 2**：2 是纯计算、体积 +0、对 OCR 路径零影响；1 需要一个评估。
4. **必须配一个用户开关**。【HANDOFF】R2 明确指出「页眉页脚过滤**目前没有用户开关**，
   误杀风险需要用真实样本量化」——**没有开关就不许默认开启激进的过滤**。

**参照**
- 本项目自己的 `filterHeaderFooter()`（`HEADER_FOOTER_MARGIN_RATIO = 0.05`、
  `HEADER_FOOTER_FONT_RATIO = 0.85`）—— **口径要一致，否则两条路径行为不可比**。
- Tesseract 官方文档的 PSM 视角（🌐 `ImproveQuality` 页）：**"整页自动分页" 与 "单栏" 是不同假设**，
  页眉页脚属于"分页"问题，不是"识别"问题 —— 这与本项目"该由版面分析回答、不该靠几何猜"的结论一致。

**验收标准**
- 需要 **2~3 份真实书籍 PDF** 量化页眉占比（【HANDOFF】R2 列的前置条件，**仍未满足**）；
- 指标：**页眉碎片占比**（`scripts/inspect-pdf.mjs` 已有该指标，🟢 脚本在仓库里）；
  目标是把"近千个碎片"降到与本项目 `filterHeaderFooter` 在 OCR 路径上相当的量级；
- **反例必须一起测**：一份**没有页眉页脚**的 PDF，过滤后**逐字节相同**。

**风险**
- **中低**。纯计算、可回退、有开关。
- **真正风险是误杀**：书眉与章节标题在几何上可能重合。**因此 ≥3 页重复这条门槛不能松。**
- **体积影响：0**（解法 2）或 **+0**（解法 1，复用已有模型，只增加运行时间）。

**为什么它排排版线的 P0**：它是**唯一一条"用户每天都会遇到、且现在 100% 会发生"**的排版缺陷。
其余（双栏、阅读顺序）只在特定文档上出现。

### P1-1 · 阅读顺序：从"版面模型给的顺序"升级到"几何可解释的顺序"

**问题**
`PP-DocLayout-S` **只给区域 + 类别，不给阅读顺序**（🌐 官方 `layout_analysis` 文档：
顺序是 `PP-DocLayoutV2` 的**级联指针网络**的职责；V2 = **203.8 MB = 25 MiB 的 814%**，
📕 与【HANDOFF】记的 203.42 MiB 一致 → **不可同源发布**）。
所以本项目现在的"阅读顺序"是靠 `applyLayoutToLines()` 里的几何排序 ——
**这恰恰是 §5.11.1 要替换掉的那类方法**，只是换了个位置活下来。

**做法**（与三·P1-2 同一套，此处是它在**排版侧**的落地）
1. **pre-mask**：用 `LAYOUT_LABELS` 里已有的类别，把 `figure` / `table` / `header` / `footer` / `page_number`
   **先从切割集合里剔除**，切完再按几何位置插回 —— 这是**本项目相对裸 XY-Cut 的天然优势**。
2. **多粒度**：页 → 栏 → 块 → 行，**不要**在词一级递归。
3. **跨模态**：用 `paragraph_title` / `doc_title` 区域与行文本长度辅助，
   避免把跨栏标题切进某一栏。
4. **不确定就退回当前行为**（逐字节）。

**参照**
- ⭐ **XY-Cut++**（🌐 https://arxiv.org/abs/2504.10258）：pre-mask + 多粒度分割 + 跨模态匹配，
  整体 98.8 BLEU，**最高超既有基线 24%**，并在新基准 **DocBench-100** 上跨简单/复杂版面表现一致。
  **它的三个改进点恰好逐条对得上本项目已有的三种原料**，这是一条**零依赖**的路。
- **PP-DocLayoutV2**（🌐 官方 `layout_analysis` 文档）：N×N 成对关系 + 胜者累积解码。
  **可以不抄模型、只抄结构**：几何投影给出的"上下/左右"关系就是一个稀疏 N×N 矩阵，
  "胜者累积"就是一个确定性拓扑排序。

**验收标准**
- **单栏样本逐字节不变**（硬要求）；
- 双栏样本整页文字流人工核对正确；
- 与 P0-1 的 `metadata` 联调：**被剔除的页眉不得出现在正文流里，但仍可回跳**。

**风险**
- **中**。同上：判错会让单栏变糟。**退回是默认** + **逐字节不变量测试**是准入门槛。

### P1-2 · 版面模型精度的**第一次真实评估**（不写功能，只产出数字）

**问题**
🟢 全仓库与 git 历史里**找不到任何一份真实页面的版面评估数据**。
【HANDOFF】§5.11.7 原话：测试证明的是「接得对、**退得回**」，**不是「判得准」**；
唯一一条正面观察只是「日志显示它多滤掉一行页脚」，**没有量化数据、没有可复现步骤**，
且【HANDOFF】明确写了「**不要把它当成"版面模型有效"的证据**」。
**这一条是 P0-1 与 P2 系列的前提** —— 没有它，任何"换模型/改判据"都是盲改。

**做法**
1. **别一上来就标 11 类**。先标**本项目真正消费的类别**：
   `header`(13) / `footer`(15) / `number`(3) / `formula`(7) / `paragraph_title`(0) / `text`(2)
   （🟢 顺序与 class_id 见 `layoutAnalysis.ts:115` 的 `LAYOUT_LABELS`，**注释明确写着顺序不能改、错一位会把页脚认成公式且不报错**）。
2. **评估集**：**用本项目自己的痛点文档**（中文扫描习题 / 教材）。
   ⚠️ **不要直接用 DocLayNet / PubLayNet**：🌐 DocLayNet 论文自己说明
   PubLayNet / DocBank「只来自 PubMed 与 arXiv，版面多样性严重不足」——
   而 DocLayNet 本身是**论文类**版面，与本项目的痛点域不同。
   **借它的方法论（COCO 格式、双/三重标注算一致性、与人比），样本自己标。**
3. **要算三个数**（缺一不可）：
   - 每个关注类别的 **precision / recall**（只看 mAP 会把"页脚全漏"藏在平均值里）；
   - **页面家具的误剔率**（被丢的里有多少是正文）—— 这是**用户唯一能感知的那个错**；
   - **人工一致性上界**：让**同一个人隔几天重标一次**，两次的差异就是你的天花板。
     🌐 DocLayNet 论文的结论是「模型比标注者间一致性低约 10%」——
     **要求模型 100% 正确是不现实的，这条给出了容错上限。**
4. **规模**：**20–50 页足够**做出第一次判断（关注的是"有没有系统性错误"，不是小数点后两位）。
5. 产出写到 `docs/` 下**新的一节**，并在 `HANDOFF.md` 里把 §5.11.7 的【未验证】改掉。

**参照**
- 🌐 **DocLayNet**（https://arxiv.org/abs/2206.01062）：80,863 页、COCO、11 类、含多标注子集，
  且论文给出**基线 mAP** 与**"模型比人低 ~10%"** 这两个可直接引用的锚点。
- 🌐 **官方模型表**（https://www.paddleocr.ai/main/version3.x/module_usage/layout_detection.html）：
  **引用 mAP 必须连评测集一起说** —— 官方自己就有 1300 / 1000 / 500 张三套口径，
  `PP-DocLayout-S` 的 70.9 出自**500 张**那套。**跨口径比较 mAP 是错的。**

**验收标准**
- 一份可复算的数字表：6 个类别的 P/R + 家具误剔率 + 人工一致性上界；
- **必须包含至少一条"模型判错"的实例**（若一条都没有，说明评估集太简单或判据写错了）。

**风险**
- **低**（不改代码）。**主要成本是人工标注时间**，20–50 页是可控的。
- 风险在于**标注口径漂移** —— 所以第 3 步的"自己重标一次"不是可选项，它是**唯一能证明标注可信的手段**。

### P2-1 · 表格：先做 Markdown 渲染，**不做**表格结构识别

**问题**
【HANDOFF】§7 P1 表：`Markdown 表格渲染` **缺失**，表格退化为普通文本。

**做法**
1. **文字层 PDF**：表格有精确的字符坐标 → 用**列投影**（x 直方图找列分隔）+ **行投影**（y 直方图）
   重建单元格网格，输出为 `remark-gfm` 能吃的 Markdown 表格
   （🟢 `remark-gfm@^4.0.1` **已在 dependencies 里**）。
2. **OCR 路径**：**先不做**。英文扫描件的表格线条可用墨迹投影检测，
   但中文扫描习题的表格常常没有完整框线，**做出来会更糟**。
3. ⚠️ **不要引入表格结构识别模型**：🌐 PaddleOCR 官方模型表里 `PP-DocLayout-M` 已经占掉 25 MiB 的 90.3%，
   **表格结构模型（`PP-Table` 系列）的体积本次未核实，但从同族模型量级看不可能再塞进来**。
   Camelot（🌐 仓库可达，lattice / stream 双模式）与 pdfplumber 都是 **Python**，
   **只能作为离线工具的参照**，浏览器里没有。

**参照**
- 🌐 **Camelot**（https://github.com/atlanhq/camelot）：`lattice`（有框线）vs `stream`（无框线）的**双模式划分**
  正是本项目该抄的判据结构 —— **先判断有没有框线，再选算法**，不要用一个算法硬吃两种表。
- 🌐 **Tesseract 官方文档**（https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html）明确写：
  「it is known tesseract has a problem to recognize text/data from tables **without custom segmentation/layout analysis**」
  —— **连 Tesseract 都不做表格**，这条支持"先只在有精确坐标的文字层路径做"。

**验收标准**
- 至少 3 份**文字层** PDF 的表格能渲染成 Markdown 且行列数正确；
- 无框线表格与有框线表格**分别**有样本；
- OCR 路径行为**不变**（不在这一条里动）。

**风险**
- **中**。"列投影找分隔"在**合并单元格**与**跨页表格**上会失败 —— **必须做"不确定就不渲染、退回纯文本"**，
  与 `ocrPiecewise` 的「KaTeX 验证闸失败就整体放弃」同一套纪律。
- **体积影响：0**（`remark-gfm` 已在树里）。

### 5.4 因为**体积**而**必须换思路**的一条：公式 OCR

⚠️ **这一条要单独说清楚，因为它是用户最初需求的直接来源。**

**问题**（【HANDOFF】§5.11.1 + `ocrFormulaRecovery.ts` 头注释）：
跨行大括号（`f(x,y) = { 上排 / 下排 }`）**整块裁剪识别不出文字** ——
识别器对该区域**返回空串**，而 `ocrEngine.ts` 对空文本是 `if (!text) continue` 直接跳过，
于是那块区域**在 `words` 里没有任何痕迹**。

**本次调研的硬结论（🌐 官方文档表，全部 HTTP 200）**：

| 候选 | 官方标称体积 | 占 25 MiB | En-BLEU | 结论 |
|---|---|---|---|---|
| `PP-FormulaNet-S` | **224 MB** | 896% | 87.00 | ❌ |
| `PP-FormulaNet_plus-S` | **248 MB** | 992% | 88.71 | ❌ |
| `PP-FormulaNet-L` | **695 MB** | 2780% | 90.36 | ❌ |
| `UniMERNet` | **1530 MB** | 6120% | 85.91 | ❌ |
| `Texify` / `pix2tex (LaTeX-OCR)` / `Nougat` | 📕 **未核实** | — | — | ⚠️ 三者均为 ViT/Donut 级编码器-解码器，**量级上不可能是 MiB 级**，但**本次一个都没核实到体积，因此不写成数字** |

**所以：浏览器端本地公式 → LaTeX 这条路，在本项目的体积约束下走不通。**
这不是"还没找到小模型"，而是**任务本身需要的模型量级与 25 MiB 差两个数量级**。

**替代方案（已经在做，且本次建议继续沿这条走）**
1. ✅ **按行带切分再识别**（`ocrFormulaRecovery.ts` / `findInkBands`）：
   头注释写明「差别不在识别能力，而在**裁剪方式**：单行识别器的输入高度固定（48px），
   两行叠在一条裁剪里时无论怎么放大都读不对」。
   **实测证据**：整块裁剪得到 `x(c) {。` / `z = {0, ≥}>Y` / `fz(e)= 0`；
   而**按行带拆开、各裁各的**，同一识别器、同一 3× 放大，输出立刻变成
   `fx(x) = fλe−x, x > 0` / `Z = {0, 当X > Y` 这类可用文本。
   **这是"用裁剪解决表示问题"，不是"用模型解决能力问题"。**
2. ✅ **"读两遍取更丰富的一遍"**（git `d0102c2`）：紧致 3× 带会丢小上标（`λe−x` 丢 `λe^{−λx}`），
   且输出随 ±2px 取景翻转 → 第二遍**横向扩 8%、2×、按精确几何绘制**，
   只在通过文本级规则（字母数字严格更多、旧读法是新读法的子序列、记号数不更少）时才换上。
3. ✅ **跨行大括号重组成 `cases`**（`ocrPiecewise.ts`）：判据全部来自实测几何
   （锚点框高 ≥ 参考字号 × 1.35、分支行横向中心落在锚点跨度内、纵向空隙 ≥ 参考字号 × 1.4、
   结构自洽要求每个构造**恰好两行**），最后**过 KaTeX 验证闸**（`throwOnError: true`），
   **渲染不出来就整体放弃，一个字不丢**。
4. ✅ **"构造符替身"语法**（git `62a5964`）：大括号上钩被认成 `≥` 时，
   因为**关系符语法上不可能紧跟 `=`**，在"标签 ="之后出现就只可能是大括号的替身
   （**`∑` 不收 —— 级数合法**）。**这是"用语法约束纠正识别错误"，同样不需要模型。**
5. ⚠️ **诚实记录边界**：`ocrPiecewise.ts` 头注释写明「本版**不发明内容**：
   识别出的字一个不增不减……上分支里丢掉的指数（`λe^{−λx}` 被认成 `λe−x`）
   **是识别本身的极限，这里不猜**」。**这条纪律必须保持。**

**下次有人再提"要不要加个公式模型"时，把上面那张表给他看，然后指回第 1 条。**

### 5.5 因为**既有决策**而不要动

| 不要做 | 依据 |

## 三、TTS 路线

> **排序判据**：用户可感知收益 ÷ 实现风险。
> TTS 这边「收益」几乎全部落在**朗读体验的连续性**上，而**风险最小**的改动恰好收益最大——因为不需要引入任何新依赖、不需要联网、不需要下载模型。所以 P0 全部是「零依赖、纯前端、可单测」的改造；神经 TTS 放到 P1，因为它带来 20 MiB 下载与一条新的可选网络路径。

### P0 · 三个零依赖改造（建议一次迭代做完）

---

#### P0-1 · 「暂停/继续」现在根本不存在

**问题**
`TTSEngine` 接口只有 `speak` / `stop` / `isSpeaking`（`src/services/ttsEngine.ts:14-21`）。`stop()` 的实现是 `speechSynthesis.cancel()`（`:140`），语义是**取消并丢弃**。UI 上仍然是「播放 / 暂停朗读」二态按钮（`src/components/ReaderView.tsx:250-252` 的 `aria-label` 在 `'暂停朗读'` 与 `'从当前位置朗读'` 之间切换）——用户按下去得到的不是暂停，而是**回到本段开头重读**。对一段 800 字的正文，这是可感知的挫败。

**做法**
1. 在 `TTSEngine` 接口上增加 `pause(): void` 与 `resume(): void`（`src/services/ttsEngine.ts:14-21`）。
2. `BrowserTTSEngine` 用 `speechSynthesis.pause()` / `resume()` 实现。**但必须同时记录「当前读到第几个 chunk、chunk 内已读了多少」**——因为 `pause()`/`resume()` 在部分实现上不可靠（见参照 2.1 的 WebKit 238189 与 SO 42875726），而本项目**已经**是「分 chunk 串行 speak」的架构，所以更稳的做法是：`pause()` = 记录 chunk 游标 + `cancel()`；`resume()` = 从游标处重新 `speak` 当前 chunk。**代价是当前句会从头重读一次**——接受它，它远好于「整段从头」。
3. `useTtsReader` 增加 `paused` 状态；`toggle()`（`src/hooks/useTtsReader.ts:99-109`）拆成 `play` / `pause` / `resume` / `stop` 四态。
4. `isSpeaking()` 需要考虑 `paused`（`src/services/ttsEngine.ts:143-145` 现在只看 `speechSynthesis.speaking`，暂停时它的行为在各浏览器不一致）。

**参照**
- WebKit Bugzilla 238189：`cancel()` 之后立刻排队的 utterance 收不到事件 → 本项目 `ttsEngine.ts:113-115` 的兜底计时器必须保留，且 `resume()` 要走「新建 utterance」而不是复用旧对象。
- Obsidian ReadAlong（2.3）：播放/暂停/上一句/下一句是**句粒度**的控制组，不是段粒度。

**验收标准**
- 一段 800 字中文正文，第 3 句中途点暂停 → 点继续 → 从**不超过 1 句**的范围内续读，而不是从段首。
- 暂停 30 秒后继续，仍然续读（验证没有被浏览器的空闲回收干掉）。
- `src/services/ttsEngine.ts` 新增 `pause`/`resume` 的单元用例，且 `src/lib/polyfills.test.ts` 那套「浏览器能力缺失时不抛错」的口径要覆盖到（当前 `polyfills.ts` 已有同类测试文件可作模板）。

**风险**
中低。主要风险是**暂停语义在三个引擎上不一致**（原生 / 云端 HTMLAudio / 将来本地模型）。缓解：把「暂停」定义在 `useTtsReader` 层的**统一语义**（「记住句子游标并停声」），各引擎只负责「停声」这一件事。

#### P0-2 · 句级高亮跟随：**不要依赖 `onboundary`**

**问题**
现在高亮的是**整段**（`src/components/ReaderView.tsx:293`），因为朗读单位就是段（`src/hooks/useTtsReader.ts:78`）。用户"听到哪读到哪"的定位能力为零。

**关键外部事实**：`boundary` 事件在 MDN 上被标为 **Limited availability，非 Baseline**（2.1 已核实）；BCD 虽然记了 `firefox: 49`，但 MDN 页面本身说「does not work in some of the most widely-used browsers」。**因此不能用 `onboundary` 作为主路径。**

**做法**（这是本项目现有架构的**自然延伸**，不是重写）
1. 新建 `src/lib/sentenceSplit.ts`：导出 `splitSentences(text, { lang }): { text: string; start: number; end: number }[]`。
   - 首选 `Intl.Segmenter(lang, { granularity: 'sentence' })`（Firefox **125+**、Safari 14.1+、Chrome 87+，2.1 已核实）。
   - 特性检测失败时退回现有 `splitForSpeech` 的规则（`src/lib/utils.ts:33-52`），并**保留原文字符偏移**。
   - 关键要求：**返回的是原文偏移**，因为高亮要靠偏移去切 `block.content`。
2. `BrowserTTSEngine.speak()` 内部改为遍历句子而不是遍历 `splitForSpeech` 的 180 字块（`src/services/ttsEngine.ts:88-93`），并在每句开始前回调 `onSentenceStart(sentenceIndex)`。
3. `useTtsReader` 增加 `playingSentence: { blockIndex: number; sentenceIndex: number } | null`，逐句 `setState`。
4. `BlockRow` 接收 `activeSentenceRange?: { start: number; end: number }`，用**已有的** `RichText` 渲染 + 一个轻量 `<mark>`/`<span class="tts-active">` 包住该偏移区间。注意 `BlockRow.tsx:99` 已有 `md = block.metadata.inline !== undefined` 的分支，两种渲染路径都要处理。
5. **`onboundary` 作为可选增强**：若浏览器真的触发 `boundary`，用它做**词级**微调；不触发就退化为句级。写在同一个模块里，用一个能力探测开关控制。

**参照**
- MDN `boundary` 事件页（Limited availability）—— 直接决定了「主路径必须是自切分」。
- Obsidian ReadAlong（2.3）：**逐句合成 + 播放器事件驱动高亮**，完全不碰 `onboundary`，效果就是「读到哪句高亮哪句」。
- 本项目已有的字符偏移能力：`BlockRow.tsx:104-121` 的 `selectionOffsets()` 已经在做「DOM selection → 块内字符偏移」的换算，句级高亮复用同一套坐标语义。

**验收标准**
- 导入一份含中英混排、含 `；`、含 `……`、含 `「」`、含编号列表的 Markdown，逐句朗读时**高亮框不跨句、不吞标点**。
- Firefox（主用浏览器）与 Chrome 上高亮推进的节奏与语音一致；**两条路径都不能出现「高亮不动」**。
- 单元用例：`sentenceSplit` 对 20 条中文难例（见 P0-3）输出的偏移拼接回去**逐字节等于原文**。

**风险**
中。最大的风险是**偏移对不齐**——`RichText` 渲染的是 Markdown 富文本，DOM 文本与 `block.content` 的原始字符串不一定同构（`BlockRow.tsx:99` 的 `md` 分支意味着有两条渲染路径）。缓解：先只对 `md === false`（纯文本块，即 PDF/TXT/OCR 来源）启用句级高亮，Markdown 块先保留段级——**先做能做的，不要一次吃掉所有渲染路径**。

#### P0-3 · 中文断句规则表（TTS 与翻译共用）

**问题**
现有切分正则 `/(?<=[。！？!?.;；\n])/`（`src/lib/utils.ts:35`）有三个明确缺陷：
1. **`.;` 的 `.` 会把 `3.14`、`v1.1`、`Fig. 2` 切开**；
2. **英文句点后的引号/括号**（`He said "Hi." Then...`）会切错；
3. **只在句末标点后切**，对 `……`（省略号）完全无效（`…` 不在字符类里），而中文长文里省略号极常见。
此外它是**纯函数、无测试**——`src/lib/utils.test.ts` 存在，但没有针对 `splitForSpeech` 的难例。

**做法**
在 `src/lib/sentenceSplit.ts` 里定义**显式的终止符集合与不切分规则**（与 `Intl.Segmenter` 结果做交叉校验）：
- **终止符**（可结句）：`。` `！` `？` `!` `?` `；` `;` `……` `…` `\n`
- **条件终止符**：`.` 仅在「后接空白 + 大写字母」或「后接 `"` `"` `'` `)` `】` 等收尾符」时结句；否则视为小数点/缩写
- **绝不切分**的位置（维护一个括号/引号深度计数器）：
  - `「」『』“”‘’（）()【】[]《》〈〉` 内部
  - 数学环境 `$...$` 与 `$$...$$`（本项目已用 `remark-math`，`BlockRow.tsx` 走 katex）
  - 行内代码 `` `...` ``
- **编号列表**：`^\s*(\d+[.、)]|[一二三四五六七八九十]+[、.]|[-*+])\s` 处**强制断句**，且该前缀**不参与**上一条的「小数点」判定
- **后缀归属**：终止符之后的收尾引号/括号**归上一句**（`「他说：『好。』」` 应为一句）
- **超长兜底**：单句 > `maxLen` 时，优先在 `，` `,` `、` 处二次切分，其次硬切——**保留 `splitForSpeech` 现有的硬切行为作为最后手段**（`src/lib/utils.ts:43-46`）

**参照**
- `Intl.Segmenter`（2.1，Firefox 125+）——首选实现，规则表作为兜底与校验。
- `pysbd`（2.3，规则式多语言分句，自带 zh）与 `wikimedia/sentencex`（2.3，MediaWiki 在用）——**规则集来源参考**；两个仓库的具体规则本次均**未取到**，实现时需再核。
- 本项目自己的教训：`HANDOFF.md` §5.12（字符级坐标）已经证明「把几何/文本事实变成可测量量」是这个项目最有效的工作方式——分句也应该有可测的难例集，而不是靠感觉。

**验收标准**
- 建一个 `src/lib/sentenceSplit.test.ts`，至少包含：`3.14`、`v1.1.0`、`Fig. 2`、`等等……然后他说「好的。」`、`（见图 3）；`、`1. 第一项`、`` `code.span` ``、`$x+y=2$`、`Mr. Smith`、`他说：「好。」` ——**每条都断言切分结果与原文偏移拼接后逐字节相等**。
- 一份真实中文 PDF（用项目已有的 `samples/`）跑一遍：扇出「平均句长」「最长句」「切分出的句子里含 `…` 的比例」三项指标，与现有 `splitForSpeech` 对比。

**风险**
低。纯函数、可单测、有明确回退（`Intl.Segmenter` 不可用时用规则表，规则表出错时用 `splitForSpeech`）。

#### P0-4 · 句间空档与滚动跟随

**问题**
`src/services/ttsEngine.ts:90-93` 是严格串行 `await`：**每句结束后才发起下一句**。原生 TTS 的 `speak()` 是同步排队、延迟很小；但 `CloudTTSEngine`（`:167-176`）是**先 `fetch` 再播**，网络往返会直接变成可听见的静音gap。朗读时页面也不会自动滚动，读到屏幕外就丢跟随。

**做法**
1. **预取下一句**：`CloudTTSEngine.speak()` 改成「播第 N 句的同时 fetch 第 N+1 句」。它已经有一个按 `lang|rate|pitch|voice|text` 为键的 Blob 缓存（`:183-186`），预取直接复用，不需要新结构。
2. 把预取做成**通用能力**而不是云端专属：在 `TTSEngine` 上开一个 `prefetch?(text, lang, options)` 可选方法；`BrowserTTSEngine` 不实现（原生排队已经够快），`CloudTTSEngine` 实现。
3. **滚动跟随**：`useTtsReader` 已经在维护块下标；把「句」下标一起暴露出来，在 `ReaderView` 里对当前句所在的块调用**已有的** `scrollToIndex()`（`src/hooks/useVirtualWindow.ts:124-146`）——注意它内部已有「平滑滚动后按真实 DOM 位置校正一次」的逻辑，句级跟随要沿用，不要另写一套滚动。
4. **暂停时不要滚**（用户暂停多半是为了看别处）。

**参照**
- Obsidian ReadAlong（2.3）：悬浮播放器 + 进度条 + 当前句高亮，滚动与播放状态是绑定的。
- Immersive Translate 的性能锚点（2.3：300 页 PDF 约 5–6 分钟）——提醒「预取」在长文档上的累计收益很大。

**验收标准**
- 云端 TTS 连续读 30 句，**相邻句之间的静音间隙 < 300 ms**（用 `performance.now()` 打点，写进会话诊断）。
- 朗读跨过 3 屏后，当前句始终在视口内；手动向上滚动后**不强行拉回**（这是所有阅读器都容易做错的地方：跟随要有「用户手动滚动即暂停跟随」的开关）。
- 预取失败（离线 / 429）时**不阻塞当前句**，只在会话诊断里记一条。

**风险**
中。预取会**提前消耗配额**（云端按字符计费，见 C5），所以必须有「预取只在用户已开启连续朗读时生效」的条件，且预取缓存要能被 `stop()` 正确回收（现在 `stop()` 会清 `objectUrls`，见 `src/services/ttsEngine.ts:257-258`——预取的 blob 也要纳入同一个回收集合）。

### P1 · 可选本地神经 TTS（唯一塞得进 25 MiB 的方案）

**问题**
原生 TTS 的两个硬伤无法在应用侧解决：① 音色取决于操作系统——`HANDOFF.md` §7 P2 已经把它记为已知限制；② **一台没装中文语音包的 Windows 机器上，`lang='zh-CN'` 的 utterance 读不出中文**（本项目 `pickVoice`（`src/services/ttsEngine.ts:267-287`）在找不到中文音色时会退回 `voices.find(v => v.default)`——**用英文音色读中文**，这是最差的结果）。③ 无法导出音频（「朗读转音频」这类需求永远做不了）。

**做法**
按项目**已有的可选重资产模式**（A1 + A2 + A4）引入 Piper 中文 x_low：

| 项 | 数值 | 对照 25 MiB 上限 |
|---|---|---|
| `zh_CN-huayan-x_low.onnx` | 20,628,813 B = **19.67 MiB**【已核实】 | ✅ 余量 5.33 MiB |
| `zh_CN-huayan-x_low.onnx.json` | 4,164 B | ✅ |
| 可选英文 `en_US-*-x_low.onnx` | **未核实**（本次只核了 lessac 的 medium=60.27 MiB 与 low=60.27 MiB，x_low 未取） | 需补 |
| `@mintplex-labs/piper-tts-web` npm | 0.47 MiB 解包【已核实】 | ✅ |
| `onnxruntime-web` | **已在依赖里**（`package.json:32`，`^1.30.0`），满足其 peer 要求 `^1.18.0`【已核实】 | ✅ |
| espeak-ng 音素化 wasm + 数据 | **体积未核实** | ⚠️ 必须核 |

1. **落盘**：写 `scripts/fetch-tts-models.mjs`，照抄 `scripts/fetch-ocr-models.mjs:80-97` 的 `FILES`（`{ path, remote, bytes }`）与 `:131-138` 的「已存在且大小相符就跳过 + sha256 校验」结构，目标目录 `public/tts-models/`。
2. **缓存**：在 `vite.config.ts:150-241` 的 `runtimeCaching` 里**加第 6 条**，`urlPattern: /\/tts-models\//`、`handler: 'CacheFirst'`、`cacheName: 'tts-models'`，**照 `ocr-models` 那条写**（关键是**不进预缓存**：`globIgnores` 要同步加 `'**/tts-models/**'`，否则 20 MiB 会被卷进首访安装体积，`verify-dist.mjs` 的预缓存检查也会亮红）。
3. **门禁**：`scripts/verify-dist.mjs` 的 `MAX_ASSET_BYTES`（`:99`）会自动覆盖到，**不需要改**——这正是先把模型放 `public/` 再构建的价值。
4. **推理**：**必须放 Web Worker**。`useTtsReader` 是 React 主线程 hook，Piper 首次推理会阻塞 UI 数百毫秒到数秒。照抄项目已有的 Worker 边界经验（`HANDOFF.md` §1「不要做」表：**PDF 解析移回 Worker 已失败三次**——但那是因为 pdf.js 的 worker 化与它自身的架构冲突；TTS 推理是**天然可 Worker 化**的纯计算，没有这个包袱）。
5. **新增引擎实现**：在 `src/services/ttsEngine.ts` 里加 `LocalTTSEngine implements TTSEngine`，`id: 'local'`，并把 `TtsPreference`（`src/store/settingsStore.ts:6`）从 `'auto'|'browser'|'cloud'` 扩为加一个 `'local'`。**`createTTSEngine`（`:298-310`）的降级链要更新**：`local` 模型未下载 → 提示「需要先下载约 20 MB 语音模型」→ 用户拒绝则退回 `browser`。**不要静默降级**——静默降级会让用户以为模型生效了。

7. **断网可用性**：走 A1 模式后，**「用过一次之后离线可用」自动成立**；但首次仍需联网——**这与 OCR 的 T1 张力完全同型**（`HANDOFF.md` §1 T1：「用过一次之后才能离线用」），必须在文档里如实写明，不要宣传成「完全离线」。

**参照**

## 四、翻译路线

> **排序判据**同上。翻译这边最大的收益不是「加新引擎」，而是**修掉一条在主力浏览器上必然报错的默认路径**（P0-1）——这是全部路线里「收益÷风险」最高的一条。

### P0 · 修正确性，不加重资产

---

#### P0-1 · Firefox 上默认翻译引擎是死路（**最值得先做的一条**）

**问题**
链条完整可查：
1. `resolveInitialEngine()`（`src/store/settingsStore.ts:107-115`）：`VITE_TRANSLATE_ENDPOINT` 为空时返回 `'browser'`。
2. `'browser'` 引擎要求 `globalThis.Translator` 存在（`src/services/translationService.ts:46-53`）。
3. `Translator` API 在 MDN 上标注 **Limited availability / Experimental**，「does not work in some of the most widely-used browsers」【已核实】；代码注释自己写的是「Chrome 138+」（`translationService.ts:33`）。
4. 不存在时 `translateWithBrowser` **直接抛错**（`:94-98`），错误文案是「当前浏览器不支持内置翻译（需要较新的 Chrome）。请改用云端翻译，或升级浏览器。」

**后果**：一个**没有配置 Worker 代理**的部署，在 **Firefox** 上——用户主用浏览器——打开译文开关的体验是：**每一段翻译都在界面上刷出一条红字错误**（错误经 `useViewportTranslation.ts:81-84` 汇入 `error`，再由 `ReaderView.tsx:408-412` 渲染成顶部错误条）。用户没有任何可操作的出路，因为 `'deepl'`/`'openai'` 在这个部署上同样不可用（`VITE_TRANSLATE_ENDPOINT` 为空）。

**做法**（三步，都不需要联网、不需要密钥）
1. **把能力检测前置到设置初始化**：`resolveInitialEngine()` 增加第三个分支——既没有云端端点、浏览器又没有 `Translator` 时，返回一个**新的 `'none'` 状态**（或让 `defaultTranslationEngine` 允许 `null`），而不是返回一个必然会失败的 id。
2. **UI 上给出可执行的结论，而不是错误**：`ReaderView.tsx:408-412` 的错误条之外，在译文开关旁给一个**一次性的静态提示**：「本部署未配置翻译服务。浏览器内置翻译仅 Chrome 支持；可以①自行部署翻译代理，②升级到 Chrome。」——把「报错」变成「说明」。
3. **`isBrowserTranslationAvailable()` 的语义收紧**：`src/hooks/useViewportTranslation.ts:159` 已经把它暴露给 UI 了，但**当前没有消费方**（grep 只在返回值里出现）。检查它是否真的接到 UI 上；没接就等于没有。

**参照**
- MDN `Translator`（2.1，已核实 Limited availability）。
- 本项目自己的先例：`resolveInitialEngine()` 的注释（`settingsStore.ts:88-106`）记录过一次**同类缺陷**——原来硬编码 `'deepl'`，导致「未配置代理的部署，用户一开译文开关就收到『未配置翻译端点』的报错」。**这次是同一个缺陷的第二次发作，只是换了一个引擎**。所以修法不能只改默认值，要有「不可用的引擎不出现在默认路径上」这条不变量。

**验收标准**
- 在**未配置 `VITE_TRANSLATE_ENDPOINT`** 的构建里，用 Firefox 打开任意文档 → 开译文开关：**界面上不出现任何错误条**，取而代之的是一条说明。
- 同一构建在 Chrome 上：内置翻译正常工作。
- 单元用例（可照 `src/store/settingsStore.test.ts` 的写法，它已经在测 `defaultTranslationEngine` 的切换）覆盖三种环境组合。

**风险**
低。纯逻辑与文案，无外部依赖。**唯一要小心的是不要顺手把 `'browser'` 引擎删掉**——它在 Chrome 上是真的能用且零成本。

#### P0-2 · `Translator` 实例复用（每块 create+destroy 是浪费）

**问题**
`translateWithBrowser`（`src/services/translationService.ts:106-111`）对**每一个 block** 都 `await api.create({...})` 然后在 `finally` 里 `destroy()`。`Translator.create()` 的语义是「准备好模型」（MDN 2.1：`create()` 是 static、`availability()` 用于检查模型可用性）。视口懒翻译一次会入队几十个块（`useViewportTranslation.ts:102-112`），并发 3，于是会**创建/销毁几十次模型会话**。而 MDN 明确提示 `destroy()` 会「Releases the resources assigned to the Translator instance」。

**做法**
1. 把 `Translator` 实例提到模块级单例，按 `${sourceLanguage}->${targetLanguage}` 缓存（`Map<string, Promise<TranslatorInstance>>`，存 Promise 而不是实例，天然去重并发创建）。
2. **`destroy()` 的时机改为**：`targetLang` 变化、`pagehide`/`beforeunload`、或显式「重置翻译引擎」。**不要**每次翻译都销毁。
3. **用 `measureInputUsage()` 做前置守门**：MDN 2.1 已核实存在 `measureInputUsage()` 与只读的 `inputQuota`。在入队前检查一句话是否超过剩余配额，超了就**停队并提示**，而不是让一堆请求失败。这一条同时解决了 P0-4 的一部分。
4. 浏览器翻译没有 `signal` 支持——`useViewportTranslation` 的 `AbortController`（`:39`）对 `'browser'` 引擎无效。要么加一个「回合序号」软取消（检查 `handledRef` 之外的一个 generation 计数），要么在 UI 上诚实标注「内置翻译不支持中断」。

**参照**
- MDN `Translator` / `destroy()` / `measureInputUsage()`（2.1，已核实）。
- `@mintplex-labs/piper-tts-web` 的 `TTSSessions`（2.2）：它专门为「更快推理」做了 session 复用——**同一个模式**，只是对象换成了 `Translator`。它的 README 把这条列为「Difference from the original」，说明这确实是一个实际痛点。

**验收标准**
- 视口翻译 50 个块，浏览器控制台里 `Translator.create` 的调用次数 **≤ 2**（不是 50）。
- 切换目标语言后旧实例被销毁、新实例被创建；内存不随块数线性增长。

**风险**
低。改动集中在一个函数。

#### P0-3 · 缓存键从 32 位升到 64 位（静默错译风险）

**问题**
`translationKey()` 用 `hashString()` = **FNV-1a 32 位**（`src/lib/db.ts:77-84`），注释明确写了「不需要抗碰撞的密码学强度」。但代价被低估了：缓存**跨文档复用**（`db.ts:34` 注释、`translationService.ts:55-62`），键空间是全局的。32 位空间在 birthday bound 下，**约 7.7 万个不同段落就有 50% 概率出现一次碰撞**；一本 300 页的书约 3,000–8,000 段，几十本书就进入危险区。一旦碰撞，用户会看到**另一本书里某一段的译文**——而且**不会报错**，因为命中缓存是「成功」路径（`translationService.ts:78-79`）。

**做法**
1. 把键换成 **64 位**（两次 FNV-1a 用不同 offset basis 拼起来，或者直接用 `crypto.subtle.digest('SHA-256', ...)` 取前 16 字节——后者是 async，但 `translationKey()` 的所有调用点（`db.ts:160`、`:170`）本来就在 async 函数里）。
2. **加自校验字段**：缓存行（`TranslationRow`，`db.ts:35-41`）增加 `sourceLength` 与 `sourceHead`（原文前 N 字符）。读缓存时比对，不一致就当未命中并重译。**这比换哈希更重要**——它把「静默错译」变成「最多多花一次翻译费」。
3. **Dexie 版本迁移**：`db.ts:50-62` 的注释已经写明「表结构变更时新增 `this.version(n).stores({...})` 即可，Dexie 会自动做增量迁移，不要直接改动已发布版本的 schema」。旧缓存行没有新字段 → 在 `version(2)` 的 `upgrade()` 里**直接 `clear()` 掉 `translations` 表**最省事（译文可以重译，代价只是钱；留着坏数据代价是错的译文）。
4. 顺带：`TranslationRow.engine` 字段（`db.ts:39`）现在只记录不生效（R15）。**这是另一个静默质量问题**——用 DeepL 翻过的段落，用户切到 OpenAI 不会重译。这**可能是有意为之**（省钱），但必须在设置页写清楚「已有译文不会因切换引擎而更新」，并给一个「清空译文缓存」按钮——`clearTranslationCache()` **已经存在**（`db.ts:178-180`），检查它是否接到了 UI 上。

**参照**
- 本项目自己的教训：`HANDOFF.md` §5.9（缺陷 21「扫描结果全丢」）的元教训是「无声无息的失败最贵」；§5.12.7「没有导出就只能靠猜」。缓存碰撞属于同一类：**它不报错**。

**验收标准**
- 单元用例：构造两个已知碰撞的 32 位输入，断言 64 位键不同、且自校验字段能拦住错配。
- `db.ts` 从 `version(1)` 升到 `version(2)` 后，在已有数据的浏览器里打开不报错、缓存被清空、重新翻译正常。

**风险**
低。但**必须处理迁移**，否则老用户的书库会读到不一致的缓存。

#### P0-4 · 字符预算可见化（C5「翻译按字符计费」目前对用户完全不可见）

**问题**
项目约束 C5 明写「翻译按字符计费，必须有缓存与按需调用」（`HANDOFF.md` §1），R4/R5/R6 确实做了缓存与懒加载。但：
- 用户**看不到**「这篇文档全译一遍要多少字符」；
- `translateAll()`（`useViewportTranslation.ts:118-121`）是**一键全篇**，没有任何代价提示；
- `progress` / `translatedCount` / `pending` 已经算好了（`:143-146`、`:33`），但没有任何「本次会话已消耗约 N 字符」的累计。

**做法**
1. 新增一个**纯估算**函数（放在 `translationService.ts` 或新建 `src/lib/translationBudget.ts`）：对未翻译的块求 `content.trim().length` 之和，乘以目标语言的经验系数（中→英约 ×1，英→中约 ×0.6，其余保守用 ×1）——**明确标注是估算**。
2. 在 `translateAll()` 的按钮上显示「全篇 ≈ N 字符」，并把 `translateAll` 从「点了就干」改成「点了先确认」。
3. **会话累计**：在 `useViewportTranslation` 里维护 `sessionChars`（每次真正走网络而非命中缓存时累加，`translateBlock` 的返回值里已经有 `cached` 字段可以判断，`translationService.ts:6-11`）。
4. **与 P0-2 的 `measureInputUsage()` 打通**：`'browser'` 引擎的配额是浏览器给的（MDN 已核实 `inputQuota` 只读属性），`deepl`/`openai` 的配额是用户自己账户的。**两者的展示必须分开**，不要合成一个「剩余额度」——那会误导。

**参照**
- DeepL `Usage and limits`（2.1，已核实）：文档翻译表里 free plans 的字符上限为 **500,000 字符**。这是最有说服力的锚点数字，适合直接放在确认对话框里。
- DeepL 的 `Estimating Character Usage` 官方文档（`https://developers.deepl.com/docs/best-practices/estimating-character-usage`，**本次未打开**）——实现时值得先读。
- Azure 的延迟数据（2.1，已核实：≤100 字符的文本 150–300 ms）：可以用来给「还要等多久」一个可信估计。

**验收标准**
- 打开一份 3 万字文档、开启译文，界面上能看到「本页 ≈ N 字符」与会话累计。
- 点「全篇翻译」先出确认框，显示估算字符数与「已有译文不计费」的说明。
- 估算值与实际消耗的偏差在**同一数量级内**（±30% 可接受，因为系数是经验的）——**不要宣传成精确值**。

**风险**
低。但**承诺的准确性要保守**：宁可把估算写宽，也不要让用户觉得被低报。

### P1 · 双语对照本身的质量

---

#### P1-1 · 句子级对齐：只对「值得」的块做

**问题**
现在**没有对齐逻辑**，因为块与译文天然一一对应（`ContentBlock.translations`，`types/content.ts:165`）。这对整段翻译是够用的。但三种场景不够：
1. `side-by-side` 布局（`BlockRow.tsx:102`）下，原文一段 ↔ 译文一段的**高度差异**会让左右两栏错位；
2. 长段落（PDF 抽出的整页文本，`HANDOFF.md` §7 提到「一本 300 页的书会产生近千个碎片」是另一头的问题）译成中文后往往**显著短于原文**；
3. 用户想「只对照某一句」。

**做法**（**明确不做 PDF 级的句级对齐**，只做块内句级）
1. 复用 P0-3 的 `sentenceSplit.ts`，对原文分句。
2. 译文按同一套规则分句，做**数量对齐**：句子数相同 → 一一对应；不同 → 退化为段落级（**不要强行按比例切**，那会产生更糟的错位）。
3. 在 `BlockRow.tsx` 的 `side-by-side` 分支里，用句级对齐结果做**逐句左右配对**，而不是整段左右并排。
4. **分页不割裂**：本项目是**块级虚拟滚动**（`useVirtualWindow.ts`），不是 PDF 分页引擎——所以「分页割裂」这个问题在本项目里**只存在于 PDF 解析阶段的块边界**，不存在于渲染阶段。这一点必须说清楚：**Immersive Translate 的分页难题不是本项目的难题**（2.3 已核实它的做法是绝对定位覆盖 + 调阈值 + 手动纠错）。本项目要防的是**解析阶段把一段正文切成两块**（`HANDOFF.md` §7 P0「文字版 PDF 的页眉页脚仍未过滤」正是这个问题的近亲）。

**参照**
- Immersive Translate PDF Help（2.3，已核实）：它的「段落识别阈值可调（行距 10px）」这条直接说明**段落重建是启发式、必须给用户可调**。本项目对应的是 `pdfParser.ts` 的段落聚类阈值（`HANDOFF.md` §5.12、R10 都在处理这条链路）。
- Immersive Translate 的 `Overlap Limit` / `Tightly Spaced`（2.3）：**翻译比原文长时的排版策略**——在左右对照布局里对应「译文列允许独立换行、不与原文行对齐」。

**验收标准**
- 在 `side-by-side` 下，一份中英对照文档的每一对句子**垂直方向大致对齐**；长度差异大时不出现「左栏第 3 句对着右栏第 5 句」。
- 句数不匹配时**整齐退化为段落级**，并在 UI 上不做任何暗示（静默降级比错误对齐好）。

**风险**
中。对齐错误**比不对齐更难忍**。缓解：句数不等就退出，不做模糊匹配。

#### P1-2 · 术语表（glossary）

**问题**
`TASKS` 明确问到术语表。本项目**零实现**（R14）。学术阅读场景里「同一术语前后译名不一致」是最容易被察觉的质量问题。

**做法**
1. **数据结构**：新增一个轻量的术语表存储（不需要新表——术语表很小，放 `settingsStore` 的 persist 里即可，避免为几百字节开一张 IndexedDB 表；但要注意 `settingsStore.ts:175-180` 的 `partialize` 已经把整个 state 写进 localStorage，术语表大了会撑爆 localStorage 的 5 MB 限额——**超过 100 条就改用 IndexedDB**）。
2. **应用方式分两条路**：
   - `'openai'` 引擎：术语表拼进 prompt。**注意 Worker 端的请求体上限**——DeepL 是 128 KiB（2.1 已核实），术语表要有条数上限。
   - `'deepl'` / `'browser'`：这两个**都不支持术语表注入**（DeepL 的 glossary 是独立 API 且要 `glossary_id`，`browser` 的 `Translator` API 没有这个参数——MDN 2.1 的接口清单里没有）。**因此术语表只能做后处理替换**，且必须明确标注「可能破坏译文语法」。
3. **诚实标注**：设置页里对每个引擎标注「支持术语表 / 仅后处理替换」。

**参照**
- MDN `Translator`（2.1，已核实）：接口只有 `availability` / `create` / `destroy` / `measureInputUsage` / `translate` / `translateStreaming` / `inputQuota` / `sourceLanguage` / `targetLanguage`——**确认没有术语表能力**，这是硬事实，不是猜测。
- DeepL 文档的结构：术语表是独立资源（`glossary_id`），意味着要么走额外 API、要么不用。**本次未核实其 CORS 影响**，但既然 `translate` 已经因 CORS 被禁（2.1 已核实），glossary 端点同理不可直连。

**验收标准**
- 添加 20 条术语，用 `'openai'` 引擎翻译：术语按指定译法出现。
- 用 `'deepl'` 引擎：UI 上明确显示「该引擎不支持术语表，已跳过」——**不要静默忽略**。

**风险**
中低。`'openai'` 路径要小心 prompt 注入与成本上升（每次请求都带术语表 → token 变多 → 钱变多，应只带**命中当前段落**的术语）。

#### P1-3 · 合并请求（省钱与降延迟）

**问题**
`translateBlock` 一次只翻一个块（`translationService.ts:63-90`）。`useViewportTranslation` 并发 3（`:50`）意味着一次视口滚动会产生几十个 HTTP 请求。每个请求都有往返开销，而 Azure 的延迟数据（2.1 已核实：≤100 字符 150–300 ms）说明**请求本身的开销往往大于翻译计算**。

**做法**
1. 在 `useViewportTranslation` 的 `pump()` 里做成**批**：一次取最多 N 个块（N 按引擎定），拼成一次请求。
2. **Worker 端要同步支持数组**：`worker/api-proxy.ts:75-131` 现在只接受单个 `text`。Azure 明确支持数组 ≤ 1,000 元素、总 ≤ 50,000 字符（2.1 已核实）；DeepL 的总请求体 ≤ 128 KiB（2.1 已核实）。**两个上限都要硬编码成常量并写进注释**。
3. **风险**：批量请求的失败是**全批失败**。必须保留「批量失败 → 拆成单条重试」的回退（对应 `worker/api-proxy.ts:127-133` 现在对 429 的处理）。

**参照**
- Azure Translator service limits（2.1，已核实：50,000 字符 / 1,000 元素 / F0 200 万字符每小时 / 无并发限制）。
- DeepL Usage and limits（2.1，已核实：总请求体 ≤ 128 KiB）。

**验收标准**
- 视口滚动触发 30 个块：HTTP 请求数从 30 降到 ≤ 10；总耗时下降。
- 批量中有一段触发 429 时，**只有那段**被重试，其余正常显示。

**风险**
中。批量的错误处理比单条复杂得多，且会与 P0-3 的缓存写入粒度耦合（缓存键是单段的，批量响应要按段拆回写入）。**建议排在 P0 全部完成之后。**

### P2 · 本地离线翻译：给结论，不给承诺

**结论：不做。** 不是「暂时不做」，是**在 25 MiB 单文件上限与「首访要轻」两个约束下不可做**。数字见下表。

| 方案 | 需要的文件（**均【已核实】**） | 单文件是否 ≤ 25 MiB | 用户一次性下载 |
|---|---|---|---|
| `Xenova/opus-mt-en-zh` int8 | encoder 50.45 MiB + decoder_merged 57.42 MiB + tokenizer 6.09 MiB + vocab 1.67 MiB + 2×spm 0.77 MiB | ❌ 两个 ONNX 都超 | **≈ 116.4 MiB**（英→中，一个方向） |
| `Xenova/opus-mt-en-zh` fp32 | encoder 200.21 MiB + decoder_merged 224.92 MiB | ❌ | ≈ 434 MiB |
| Mozilla Bergamot | **中英模型是否存在本次未核实**；`firefox-translations-models` 仓库 README 已声明 **not maintained anymore**（已核实），模型迁到 `mozilla/translations` + GCS | 未知 | 未知 |
| LibreTranslate | **未核实**（自托管为主） | — | — |

**为什么不把 Bergamot 也下结论**：`mozilla/firefox-translations-models` 已归档，语言清单要看 `mozilla.github.io/translations/firefox-models/`，而那个页面靠 JS 拉 JSON 渲染，**本次抓取失败**（页面显示 "Error fetching the models"）。所以「Bergamot 有没有中英」这条**未核实**。但即使有，Bergamot 的模型是 **Marian intgemm 格式（`.bin`）**、需要配套的 bergamot-translator WASM 运行时与 vocab 文件——**它不是一个能放进本项目的 npm 依赖**，而是一整套自建推理栈。对一个单人维护、零后端的项目，这个投入产出比不成立。

**如果将来一定要做**，正确的形态不是「塞进 PWA」，而是：照 `mozilla/translations` 的方式，把模型放在**与站点同源的 CDN 路径**（本项目已有 `public/ocr-models/` 的范式，但 116 MiB 不可能进 Cloudflare Pages 单文件），并且**必须复用 Timeline Studio 那套分片 + SHA-256 + 双镜像 + 缓存升级**（2.3）——那套工程的存在本身就说明「几百 MB 的浏览器模型」不是加个 `npm install` 的事。

## 五、与「不把文档送离本机」原则的冲突分析

### 5.1 逐方案的联网/外发判定

| 方案 | 需要联网？ | 有字节出本机？ | 出去的是什么 | 默认应是什么 | 依据 |
|---|---|---|---|---|---|
| 浏览器原生 TTS（现状） | ❌ | ❌ | — | **默认** | `speechSynthesis` 是本地系统语音 |
| **句级高亮 / 断句 / 暂停续读**（本路线 P0 全部） | ❌ | ❌ | — | **始终开启** | 纯本地字符串处理 |
| 本地 Piper 模型（P1） | **仅在首次下载时** | ❌（只**下载**，不上传） | 无文档内容；只有 HTTP GET 模型文件 | **可选**，默认不用 | 与 OCR 模型完全同型（`HANDOFF.md` §1 T1） |
| 云端 TTS（现状 `CloudTTSEngine`） | ✅ | ✅ | **被朗读的正文文本**逐段 POST 到自建 Worker，再由 Worker 转发 Azure | **可选**（现在是 `auto`：配了端点就自动用） | `src/services/ttsEngine.ts:156-219`、`worker/api-proxy.ts:184-238` |
| 翻译 · `'browser'`（Chrome `Translator`） | 首次可能要（模型下载） | **取决于实现**——但按 MDN，它是浏览器厂商的端上能力，**API 本身不要求你把文本发给第三方服务** | 未核实的部分：Chrome 是否上报遥测 | 可选 | MDN `Translator`（2.1） |
| 翻译 · `'deepl'` / `'openai'`（现状） | ✅ | ✅ | **被翻译的段落文本**，经自建 Worker 转发到 DeepL / OpenAI | **可选** | `src/services/translationService.ts:114-138`、`worker/api-proxy.ts:75-131` |
| 公式 OCR（`formulaOcrEnabled`） | ✅ | ✅ | **页面局部像素**（裁剪出的公式区域 PNG） | **默认 `false`**（已拍板） | `src/store/settingsStore.ts:39-58`、`:145`；`worker/api-proxy.ts:243-290` |
| 浏览器内离线 NMT（**本路线明确不做**） | ❌ | ❌ | — | — | 见 §4 P2 |

### 5.2 核心冲突：**这个项目现在有三条上传路径，只有一条是 opt-in**

这是本节最重要的一条事实：

| 上传路径 | 当前默认 | 用户是否被明确告知 |
|---|---|---|
| 公式 OCR → SimpleTex | 默认 **关**，显式勾选 | ✅ 有复选框、有注释、有第二道防线（`recognizeFormula()` 关闭时抛错，`HANDOFF.md` §5.8） |
| 云端 TTS → Azure | **`ttsPreference: 'auto'`（`settingsStore.ts:136`）**：只要构建时配了 `VITE_TTS_ENDPOINT`，**朗读就用云端** | ❌ **没有任何告知**。用户点「朗读」时不会知道自己的正文正在被 POST 出去 |
| 云端翻译 → DeepL / OpenAI | 打开译文开关即触发（但需用户主动开 `showTranslation`，`settingsStore.ts:132` 默认 `false`） | ⚠️ 半告知：译文是用户主动要的，且项目定位写着「双语对照」；但**界面上没有一句话说明「这会联网」** |

**「文档全程不离开浏览器」这句写在 manifest 里的话**（`vite.config.ts:60-61`：`description: '……文档全程留在本机浏览器，不上传服务器。'`）——在同时开启了云端 TTS 或云端翻译时，**这句话是不准确的**。`HANDOFF.md` §1 的 T2 只把公式 OCR 认定为「唯一」外发路径，**那是把 TTS 与翻译排除在外了**——因为它们的「外发」被视作功能本身。这个口径需要显式化，否则下一个人会继续按「唯一路径」去读代码。

### 5.3 怎么给用户选择：把已有的范式推广成一条统一规则

`formulaOcrEnabled` 那套做法（§5.8 已拍板）**已经是一个完整的、经过验证的范式**，把它的四个要素抽出来：

1. **默认关闭**（`false`）
2. **显式 opt-in 的 UI 控件**（对话框里的复选框）
3. **第二道防线**：代码层在关闭时**主动拒绝**，而不是靠调用方自觉（`recognizeFormula()` 关闭时抛错）
4. **代价透明**（复选框旁的说明文字讲清「会上传什么」）

**建议把这条规则推广成不变量**（写进 `HANDOFF.md` §1，作为 C3 的可执行版本）：

> **任何把文档内容送出本机的代码路径，必须：① 默认关闭；② 有显式 opt-in 控件；③ 在代码层有第二道防线；④ 在 UI 上说明「上传了什么、去哪里」。**

按这条规则，本路线图要做的具体动作：

| 动作 | 位置 | 说明 |
|---|---|---|
| ① 云端 TTS 的默认值从 `'auto'` 改为不自动启用云端 | `src/store/settingsStore.ts:136`（`ttsPreference`） | 现在是「构建时配了端点就自动用云端」。改成：`auto` 时若云端点存在，**第一次朗读前弹一次一次性的确认**，讲明「将把你的正文发送到语音合成服务」 |
| ② 译文开关旁加一行常驻说明 | `src/components/ReaderView.tsx` 译文控件附近 | 一句话：「译文由 DeepL / OpenAI 生成，正文会离开本机。切到『浏览器内置』可避免。」 |
| ③ 云端引擎在代码层的第二道防线 | `src/services/ttsEngine.ts:298-310` + `worker/api-proxy.ts:184` | `CloudTTSEngine` 构造时检查一个显式开关（新设置项 `cloudTtsEnabled`）；Worker 端可选加一个「仅允许已授权来源」的字段校验 |
| ④ **审计视图**：一个「本机外发记录」列表 | 新模块 + 复用 `src/lib/sessionDiagnostics.ts` 的落盘方式（A6） | 记录每次外发：时间、路径（`/api/tts` / `/api/translate` / `/api/formula-ocr`）、**送出了多少字符/多少字节**、去哪。`HANDOFF.md` §1 T2 明确记着「应用内**没有**『上传了什么』的审计视图」是尚未收口的残余点——**这个缺口现在变成了三倍的缺口** |

**第 ④ 项是本节最有价值的一条**：它一次性把三条路径的残余点全部收口，而且**不需要改任何上传逻辑**——只是把已有的事实记下来给用户看。成本极低，收益直接落在产品最核心的卖点上。

### 5.4 不需要用户选择的部分（要敢于标为「无冲突」）

- 本路线图 §3 的 **P0-1 / P0-2 / P0-3 / P0-4**：全部纯本地，零网络。
- §4 的 **P0-1**（修 Firefox 死路）：纯逻辑，零网络。
- §4 的 **P0-3**（缓存键）：纯本地，而且**降低**了错误风险。
- §4 的 **P0-4**（字符预算）：纯本地计算，**提升**了用户对网络成本的可见性。
- §3 的 **P1**（本地 Piper）：**下载**模型 ≠ **上传**文档。这两件事在用户认知里常被混为一谈，UI 文案要主动区分：「下载约 20 MB 语音模型（只下载，不上传你的文档）」。

## 六、明确**不做**的

| 不做 | 理由（数字为本次【已核实】实测） |
|---|---|
| **引入 Kokoro 作为阅读 TTS** | 最小的可用变体 `model_int8.onnx` = **121.46 MiB**，fp16 = **156.05 MiB**，fp32 = **323.65 MiB**——**任何一档都远超 25 MiB 单文件上限**，必须走第三方 CDN。而「读文档」这个场景对音色的边际收益远小于「离线可用 + 零下载」的价值。**若将来真要做，参照物是 Timeline Studio 那一整套分片/校验/双镜像/缓存升级工程（2.2），不是一个 `npm install`。** |
| **引入 sherpa-onnx WASM + 中文 VITS** | `vits-aishell3.int8.onnx` = **38.02 MiB**（单文件已超限）；fp32 = **115.76 MiB**；`lexicon.txt` = **1.95 MiB**；`rule.far`（数字/日期文本正则化）= **172.34 MiB**（可省，但省了数字会读错）。加上 WASM 运行时（**体积未核实**——官方 wasm/tts 文档页本次返回 404）。**四份资产全部要管，收益只是一个中文音色**，而 Piper x_low 用 **19.67 MiB 一个文件**就给了同样的东西。 |
| **浏览器内离线 NMT（opus-mt / NLLB / Bergamot / argos）** | 最省的 `opus-mt-en-zh` int8 = **50.45 + 57.42 = 107.87 MiB** 的两个 ONNX（单文件双双超限）+ **9.3 MiB** 分词器；fp32 是 **425 MiB**。Bergamot 的 `firefox-translations-models` 仓库 README **已声明停止维护**（已核实），语言清单未能核实。**这不是「以后再说」，是在本项目两个硬约束下不可行。** |
| **把译文重新排版回 PDF（覆盖式双语 PDF）** | 连这个领域最成熟的商业实现（Immersive Translate，2.3 已核实全文）都是：绝对定位文本框覆盖在 canvas 上 + 用户手动拖动/删除/缩放/重译 + 段落识别阈值可调 + **导出双语靠截图** + 官方承认公式和表格识别不了 + 建议不超过 300 页。**本项目的架构优势恰恰是「PDF 已经解析成 block 流」**——回到像素层覆盖是**主动放弃自己最强的地方**。 |
| **语音克隆 / 情感 TTS（ChatTTS / CosyVoice / GPT-SoVITS / Fish Speech）** | 这些在本项目的运行环境（浏览器）里**没有推理路径**。本次**未逐一核实**其体积，但这一点不影响结论：它们的推理栈是 PyTorch + Python，不是 ONNX/WASM。**在没有核实之前不要写进任何路线图当作候选。** |
| **用 User-Agent 嗅探判断 TTS / 翻译能力** | 沿用 `HANDOFF.md` §1「不要做」表已拍板的规则：同一款外壳浏览器的「极速模式」与「兼容模式」内核完全不同，**只检测能力**。本路线图全部用特性检测（`'speechSynthesis' in window`、`Intl.Segmenter` 存在性、`globalThis.Translator` 存在性）。 |
| **把 `crossOriginIsolated` 当 TTS/翻译的可用性判据** | 同 `HANDOFF.md` §1：它只影响多线程。本项目推理是单线程（`ort.env.wasm.numThreads = 1`）。**只记录，不判定。** |
| **把 TTS/翻译模型塞进预缓存（precache）** | 单文件预缓存上限是 `5 MiB`（`vite.config.ts:113`），而 `maximumFileSizeToCacheInBytes` 超限时 workbox **只警告不报错**——这是 `HANDOFF.md` §3 记过的坑。同时 `verify-dist.mjs:230-245` 已有「不该预缓存的资产」检查。**必须走运行时 `CacheFirst`**（A1/A4）。 |
| **加云同步的术语表 / 译文记忆库** | 与 C3 直接冲突。若真要做，必须端到端加密（`HANDOFF.md` §1「不要做」表已定调）。**术语表就留在本机。** |
| **给翻译加「自动全篇翻译」的默认行为** | C5 是按字符计费。`translateAll()` 必须是**用户显式点击 + 代价确认**（见 §4 P0-4），不能因为「用户体验更顺」就自动触发。 |
